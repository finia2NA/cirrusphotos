# Architecture

This document is the source of truth for current technical structure, subsystem boundaries, data flow and invariants. User-visible behavior is in [PROJECT.md](PROJECT.md); server request shapes are in [SYNOLOGY_PHOTOS_API.md](SYNOLOGY_PHOTOS_API.md); how that API behavior was established is in [capturefindings](capturefindings/README.md). Keep each section short and name a type only when it is an entry point to the code.

## Overview

| Module | Role |
| --- | --- |
| `TimelineCore` | Platform-independent models and geometry: day navigator, fixed photo grid, viewer transform and dismissal math, map clustering. |
| `SynologyAPI` | Wire and domain models, the `PhotosTransport` contract, the concrete authenticated `SynologyClient`, credentials, diagnostics. |
| `PhotoCache` | `CachedPhotosRepository` (the actor every consumer talks to), the metadata engine, GRDB-backed `DiskCache`, selection resolvers, `PhotoViewerSession`, `LibraryIndex`/`LibraryPageWindow` and the filter controller. |
| `CirrusPhotosApp` | The SwiftUI/AppKit executable (`CirrusPhotos`, built as the Cirrus Photos app bundle). |
| `TransportTestSupport` | Test-only `TestPhotosTransport` with a failing default for every request a test does not implement. |

Large targets group files by subsystem (`PhotoCache/Metadata`, `CirrusPhotosApp/Viewer`); `CachedPhotosRepository` extensions sit with their subsystem and test folders mirror them. Dependencies point downward in that order. Each open account has one `CachedPhotosRepository`, and the UI reaches the NAS only through it. SwiftUI hosts the shell, an AppKit viewport virtualizes the browser, AppKit/Core Animation draws the viewer canvas and AVFoundation plays repository-backed video ranges.

## Invariants

These hold across subsystems and are not obvious from any one file.

1. **Cached-first, NAS-authoritative.** Repository reads are finite typed `AsyncStream`s: the cached value first, the current value after validation, then finish. Cached reads never wait for login or a network slot. Cached metadata is provisional until validated, and stale content stays usable when validation fails (offline, slow, or a server error). Each resource is validated at most once per run; nothing polls for external changes. The manual Refresh withdraws only this run's validation; it never clears the cache.
2. **Fencing.** Every asynchronous metadata write carries a `MetadataWorkToken`: repository admission, storage and reset generations, job identity and the relevant mutation epochs. SQL admissions also bind the destination namespace and its revision/reset epoch. Transactions never suspend. A stale admitted write cannot overwrite newer confirmed fields; local mutation patches tolerate earlier local revisions but keep namespace and reset fencing.
3. **Diff feeds are the only cross-run freshness proof.** A terminal Diff v7 interval of at most 2,000 changed IDs and 4 MiB can advance the cursor together with replacements and deletions. A partial, oversized, malformed, unsupported or rejected interval invalidates coverage centrally and falls back to authoritative reads. No feature owns a cursor. Details in [Repository and metadata engine](#repository-and-metadata-engine).
4. **Nothing defaults to Personal Space.** Every transport, repository and app method that works in a space or collection takes it explicitly. Album items have no inferred origin space.
5. **Verified selections.** Actions on photos (favorite, rotate, tag, rate, delete, download, add to album, edit) run on a selection resolved by one verifier that proves membership by ordered IDs, fingerprint and item identity. A changed fingerprint, identity or membership replacement fails the action instead of acting on different photos.
6. **Writes end in a read.** Every NAS change is followed by an authoritative read of what it touched, even after failure or cancellation. An uncertain outcome is reported as `unconfirmed`. Creation is never retried automatically. Only one write runs per `MutationLane`; a second fails with `RepositoryError.busy`.
7. **Capture-local time.** `PhotoItem.time` is a capture-local wall clock encoded as epoch-shaped seconds, not an instant. Grouping and formatting use GMT calendar components so 21:00 displays as 21:00 on any Mac. No timezone is inferred from location or device.
8. **Pre-1.0 formats are disposable.** Incompatible preferences, navigation state and cache schemas are discarded and recreated; metadata formats are discarded without decoding. Media bytes keep their format.
9. **Logs hold no secrets.** Diagnostics exclude filenames, cache keys, credentials, tokens, session IDs, cookies, authenticated URLs and response bodies. Sharing references are never persisted in album summaries. `LogExport` streams `log show` through `LogRedaction.scrub` line by line (fallback `OSLogStore`, this process only).

## Transport

`PhotosTransport` is the repository's only NAS dependency (login, timelines and pages, indexes and folders, albums and sharing, annotation, rotation and deletion writes, uploads, media, downloads, video ranges, Diff feeds); `SynologyClient` implements it. Every JSON call goes through one `request`/`call` path that adds the session and maps envelope errors; `SynologyClient.api(_:_:)` picks the `Foto` or `FotoTeam` API by space. Large transfers report byte progress through delegates, treat timeouts as inactivity limits and read the session through one accessor. Responses are bounded.

**Sign-in.** `SynologyCredentials` carry a `SecondFactor` (none, `.env` TOTP secret, typed code, device token) and a `ServerTrust`. Login uses the `webui` session and device name "Cirrus Photos"; a typed code also requests a device token (`did`), sent later as `device_id` instead of a code; DSM's 403 becomes `secondFactorRequired`. The client keeps renewal credentials (a code replaced by its token), renews once per expired session (106, 107, 119) for every JSON call and retries; failed renewal is reported through `onSessionRenewalFailure`. The repository maps rejected credentials and codes to `AuthenticationStatus.needsSignIn`, refused certificates to `.untrustedCertificate`; other rejections stay failed until retried, unreachability retries on the next request.

**Transport security.** `CirrusTrustDelegate` applies to the NAS host only: system validation, else a user-accepted pinned leaf SHA-256; a refused certificate reports its fingerprint. `AccountController` asks before connecting and pins the fingerprint on the stored account, or per host in defaults for `.env`. Only development bundles carry an ATS exception, for the `.env` host ([Build modes](#build-modes)). Cookies are ephemeral.

Request shapes, versions and what each was verified against are in the API reference, not here.

## Identity and scopes

`PhotoSpace` is Personal or Shared. `PhotoContentScope` is either a space or an unresolved album authority (an owned album ID, or an incoming album's owner and album IDs). `PhotoItemIdentity` pairs a scope with an item ID. Unit IDs are separate media-resource identities. `owner_user_id` is kept as server evidence but never used as an origin discriminator.

`PhotoCollectionDescriptor` identifies a collection: Library, Favorites, Folder, Person, Subject and Tag carry their space; Album descriptors keep contextual authority and expose no inferred space; Map and filter descriptors carry their source space or scope and registration rejects a mismatch. `MetadataNamespace` requires an explicit scope; `CollectionKey` combines it with the descriptor. The normalized tables, page and thumbnail keys, original and video resources, mutation events and observer streams are all scoped, so Shared Space, Personal Space, each owned album and each incoming album have isolated metadata, media and mutation authority. Media transport rejects a scope it does not support before sending a personal request.

Shared Space reconciles its own Diff feed and keeps its own inventories, favorite overrides, pending writes and refresh jobs. Personal mutation and invalidation broadcasts never touch shared pages. Space selection persists separately from the destination. Which Shared Space endpoints are captured and which are inferred is listed in the API reference.

## Repository and metadata engine

`CachedPhotosRepository` is the sole coordination actor. State is split into owned structs (authentication, `MetadataEngineState`, image work, favorites, item mutations); actor-isolated extensions hold the authentication, metadata, media, favorites and rotation pipelines so suspension points and ordering stay on one actor. `isAdmitted(_:)`/`requireAdmission(_:)` are the single admission-epoch check.

**Layout.** A day catalog (`CollectionDayCatalog`) validates NAS Timeline sections into unique capture-local days and counts. `CollectionDayPager` emits one logical page per day with capacity 250; `DayPageAddress` is collection, day, day-local offset, capacity and order, and excludes section index, count and fingerprint. Catalog revisions and per-day membership generations are independent: inserting an unrelated day keeps older slots, while any change inside a day invalidates that day's membership. Albums yield the same catalog from an item scan, because the Timeline endpoint ignores `album_id`.

**Tables.** Identity/time/GPS projection (`item_index`), canonical details with annotation authority (`item_details`), catalogs and day generations, exact ordered `day_pages` and reverse `page_items`, plus summaries. Evicting a detail leaves every known ID and ordinal in place, so a page is a list of exact slots that may be unloaded. `PhotoPageSnapshot` carries membership verification and per-slot details; per-slot verification governs media and actions.

**Reads.** `MetadataReadPlanner` batches up to 1,000 contiguous demanded items across at most 32 days with no gap padding, and the engine keeps two physical network slots. Detail jobs are keyed by `PhotoItemIdentity` so consumers share work, cancellation and priority promotion without joining distinct scopes. A coverage mismatch joins one collection recovery and gets one retry. Album actions request fresh contextual details, which supersede older in-flight authority.

**Diff reconciliation.** Each space has its own feed (`Browse.Diff` v7 `get_version`/`list`, independent cursors, `MetadataSourceState`). Modified IDs are looked up in batches of 100 and fenced; an empty interval commits only the cursor. `item.merge` lists bare IDs (a Live Photo's short-lived video item folded into its still): merged IDs are looked up with the modifications, present means replacement, absent means deletion. Because that meaning is inferred, an interval with merges compares a complete inventory with the day-catalog count and resets on mismatch. `item.move`, `similar`, non-integer merges and unknown user events recover through authoritative reads. The favorite-event feed (`list_user_event`) is read after the item feed from the same cursor, so the committed cursor never skips a favorite event; any other event type recovers.

**Proof run.** A successful reconciliation records `metadata_state.proof_run`. A cached page is then verified without a read when stored under the current reset epoch, its day generation and count match, its catalog was validated this run, and the collection is a Library, folder or general tag (either space) or Personal Favorites; cached details share the proof. A changed ID without an index row invalidates the days of pages listing it. Untouched folder catalogs are validated too, when validated in an earlier run under the current epoch, fully listed by stored pages, and holding no changed or deleted item before or after (a replacement without `folder_id` disables this).

**Proven albums.** An unshared owned album's catalog records the album `version` it was stored under; an unchanged version validates it. Album-context detail copies are proven once both spaces reconcile, since each reconciliation marks album copies of changed IDs stale; Shared Space has no favorite feed, so copies of its members can miss favorites changed elsewhere. Shared albums, People, Subjects, Recently Added, incoming albums and Shared Favorites always read this run.

**Background work.** `MetadataSyncModel` starts once Personal Library and Favorites are verified. It and the section warmer re-check start conditions through Observation, so every `LibraryModel` property they read, including `repository`, must be tracked. Each pass discovers the warmer's targets, owned albums and the breadth-first folder trees (five albums or folders at a time) while a loading loop reads the pages of each target as soon as its timeline is known, through the cached-first path at prefetch priority, current collection first, then library targets. An incomplete pass repeats after 30 seconds doubling to 10 minutes, or when `NWPathMonitor` reports the network. A running pass holds an `ActivityKind.metadataSync` entry with discovery and section stages (updated at most once a second, discarded at the end, never in History). `TimelineSectionCacheLoader` runs the same engine with a 64-page lookahead.

**Filtering.** A filter is a session-only collection derived from Library, Favorites, an album, a folder or a Map result. `LibraryFilterController` reads the facet columns on `item_details` (including a folded filename key) for the whole source in one read with normal page verification, so it works offline; Map and filter-derived sources read cached pages network-disabled in batches of 64. It has no scan of its own: it observes coalesced page commits and indexes whatever was stored, rereading facets once the source is verified. A `.libraryFilter(UUID)` registration keeps ordered IDs and source references; source verification gates each slot and invalidation withdraws membership. Camera, lens and extension suggestions are cached per account and collection and merged when coverage is incomplete.

**Collection indexes and folders.** People, Subjects and Tags share one kind/entry type. Index and folder-directory jobs are keyed by space, share cached-first admission, persist complete listings per namespace and keep the previous listing on failure; their IDs are ordinary collection descriptors. A folder directory is the folder summary plus a paged `Browse.Folder list`; the root resolves its ID with `get`, and the sync passes children the summary from a parent listing verified this run. Listings are read once per run (no feed reports folder changes). Folder covers are derived from cached directories and pages, stored in `folder_covers` and recomputed once per run. Recently Added groups by `indexed_time` day and fails closed when it is missing or inconsistent.

## Cache

`DiskCache` owns a GRDB `DatabaseQueue` (WAL, `synchronous=NORMAL`). `CacheSchema.swift` declares every table as a Codable record; nested values are JSON text; storage code uses the query interface, not hand-written SQL ([decision 002](decisions/002-grdb-records.md)). Storage methods are synchronous so no transaction suspends. Compressed images and video segments are hashed files under an account-scoped directory of the build mode's `CacheLocation` root ([Build modes](#build-modes), [decision 001](decisions/001-development-cache-location.md); changes with #84). The index has an explicit schema version; an incompatible or unreadable index and its media files are recreated from NAS data. Rows record validation run, access time, ETag, Last-Modified, content digest and a monotonic revision.

**Reset scopes.** A metadata-only clear advances the storage generation at admission, removes metadata rows transactionally, broadcasts an invalidation revision only on success, and preserves media and transfers already admitted. Full clear also advances the whole-cache generation, removes media and cancels media work. Deleting items uses the metadata-invalidation scope too, so the UI reloads as after a metadata clear.

**Budget.** Every normalized write enforces the budget after commit. Eviction removes video segments, then viewer previews, full images, thumbnails, details and membership, compact inventory and finally catalogs; evicting the compact index clears inventory completeness. Usage is an in-memory estimate: media writes adjust it exactly and metadata is re-measured at most every 15 seconds; budgets of 200 MB or more keep a reserve, smaller ones scan on every write. Read recency is batched and flushed before eviction. The budget counts media payloads plus metadata column lengths, not SQLite overhead or block rounding, so the directory is a few percent larger (about 4% on 12 GB). The budget applies per account.

**Validators.** Original GETs send `If-None-Match`/`If-Modified-Since` when validators are cached and accept `304` only with local bytes. Thumbnails are versioned by the NAS `cache_key`, which is part of the cache identity: an exact cached thumbnail is current once its descriptor comes from metadata verified this run, so thumbnails are fetched only on a cache miss and send no validators. Preview and ordinary `xl` thumbnails share a key and file; ordinary demand promotes the category and preview work cannot demote it.

## Browser

One virtualized browser serves Library, Favorites, folders, People/Subjects/Tags results, Recently Added, opened albums and filtered or Map results.

**Data flow.** The repository publishes day-grouped page snapshots. `LibraryIndex` maps each day to exact slices of section responses with page-, day- and collection-ordinal coordinates, rows and directional destinations. `LibraryViewportGeometry` derives height and slot positions from counts, the column count and day grouping before metadata loads; only hit rectangles depend on loaded items. With grouping off, ordinals fill one continuous grid without headings and each slice owns the rows that start in it. `LibraryPageWindow` keeps viewport pages plus up to eight prefetched, emits cached pages promptly, rejects obsolete responses, and rebases by address on typed day invalidation.

**AppKit viewport.** An `NSScrollView` hosts a flipped document that creates date headings and pooled layer-backed `BrowserPhotoCellView`s only for the visible region plus overscan; the cell is the keyboard focus, accessibility element and viewer-transition source while pointer input passes through to the document. A cell shows cached bytes first, validates after current page metadata arrives, keeps a displayed rendition visible while validating, and loads off the main thread with cancellation on reuse. An AppKit overlay draws selection and marquee feedback. Scroll position is restored by visible item ID plus pixel offset, else by date and slice. `BrowserScrollIntentCoordinator` owns a single typed restoration, preservation, reveal or selection-navigation intent; newer intents replace older ones and user scrolling cancels refinement.

**Limits.** Six thumbnail transfers and five metadata requests run concurrently (`NetworkGate`), visible demand before prefetch, with bounded queues; shared jobs cancel when their last subscriber leaves, and a thumbnail miss with no job in flight re-reads the cache before starting one, so a transfer that just finished is not repeated. ImageIO downsamples off the main actor through a gate of four concurrent decodes that runs the newest request first, and an `NSCache` bounds retained decoded images. `LibraryModel` uses Observation; per-collection timeline state is announced by one revision, coalesced to once a second while warming.

**Selection.** `LibrarySelection` is a session-local set of ordinal ranges per collection, so selecting a whole collection never materializes metadata. The key window's AppKit responder dispatches the same commands as the Library menu. Membership signatures invalidate an ordinal selection when order or membership changes. Selection survives recycling, scrolling, resizing and switching destinations.

**Navigator.** The equal-day track gives each populated day the same fraction of the track, so pointer lookup is a constant-time index and some days cannot be targeted by pointer when days outnumber pixels; keyboard and accessibility actions step single days. User input creates a jump request with a fresh identity; scroll feedback updates the selected day without a jump. After an index change the nearest remaining older day is used.

## Viewer

`PhotoViewerSession` is the single actor for viewer coordination. It navigates an immutable `LibraryIndex` using section-prefix counts, keeps at most three metadata pages (`ViewerMetadataWindow`) and the current plus two adjacent encoded originals (`ViewerImageWork` owns bytes, tasks and shared cancellation). Selection generations on replayed snapshots and request tokens reject obsolete results during rapid navigation. Verified metadata preserves the selected item by ID when its page moves; provisional metadata may read cached images but cannot authorize downloads. A changed authoritative snapshot invalidates ordinary navigation with an explicit reopen state while the presentation keeps its decoded image; a missing selected detail keeps the displayed image. A Favorites viewer keeps its opening playlist while membership changes.

**Image policy.** The viewer shows the configured thumbnail at once and reads cached `xl` previews and originals immediately. Network `xl` and original requests start after the selection is stable for 100 ms, then run concurrently and warm one adjacent `xl` each way; two slots allow one speculative request, and selecting an in-flight neighbor promotes it. Neighbor originals are fetched only after the current one succeeds and stay compressed; neighbor thumbnails and previews may be decoded ahead. An `xl` upgrade survives a failed original; a decoded original is final; an unavailable original retries every two seconds. `FullImageDecoder` decodes off the main actor, one decode plus one replaceable waiter, rejecting images above 384 MB decoded.

**Canvas.** A layer-backed AppKit canvas holds a backdrop and an image layer whose contents change only with the image identity. `PhotoViewportTransform` supplies fit, zoom and pan; transitions animate only position, bounds and opacity, starting from the presentation layer. Three reusable layers carry the horizontal swipe; the dismissal gesture (direction lock, response from `PhotoViewerDismissal`) ends in the same close pipeline as Back/Escape, all driven by one phase value. Reduce Motion uses a fade. Opening starts from the thumbnail's window rectangle; closing resolves the live cell, else fades.

**Status.** `ViewerStatus.make` combines the shown image tier, the session's full-image status, decoding, transfer progress, the stall flag and video playback status into the toolbar title text and progress. `ViewerStatusModel` is observed separately so progress does not redraw the viewer. Progress is network-only (`fullImageProgress` follows the shared transfer regardless of who started it), moves forward only, and a load with no data for 8 seconds is marked stalled.

**Inspection overlays.** The filmstrip reuses the browser's thumbnail geometry and the viewer's bounded metadata window. The histogram and the two GPU overlays (highlight peaking, focus edges) work on the displayed image off the main actor: `ViewerGPUImageRenderer` resamples to a bounded raster, runs an effect shader (an optional statistics pass for focus edges), and reads back a small overlay. Requests are serialized; cancelled work is discarded before publication; selection changes hide old overlays. Peaking marks rendered near-white pixels by a 5% HSV-saturation tolerance, which is a heuristic and not a raw-clipping detector.

## Media

**Thumbnails and originals.** Thumbnail, original, preview and video resources have semantic keys that include the account namespace, scope and revision. Thumbnail renditions follow the user setting; compatible fallback renditions stay visible until the selected one arrives. The viewer's handling of originals and previews is described above.

**Video.** `VideoQualityPreference` is semantic; Automatic targets High. The effective rendition is the nearest advertised quality (lower wins a tie); Original is a separate stored file and the fallback when nothing converted is advertised. Cached 64 KiB segments are served first and contiguous missing demand is fetched in windows of at most 1 MiB on a separate two-transfer lane; a shared window replays bytes to concurrent subscribers, stops when the last leaves, and persists segments only after validation. An ETag, Last-Modified or length mismatch purges the rendition and fails as stale. Nothing is prefetched for adjacent videos, and a new network range needs verified metadata. `VideoAssetLoader` maps AVFoundation requests to the repository through an opaque custom-scheme URL, so credentials never reach AVFoundation. A failed converted playback falls back once to the original.

**Live Photo motion.** Motion waits for the full still and verified metadata. An indicator click or Force Touch press looks up the item's `Browse.Unit` members on demand (never persisted, so it needs a connection), picks the converted rendition nearest High and streams it through the same range cache. Lookup is fenced by selection generation. In an owned album the member's space is first verified with the member-origin read used for item actions. Motion is suppressed when Synology's display orientation differs from the original's.

**Downloads and export.** `PhotoDownloadManager` runs independent cancellable jobs; the client streams each response to a temporary file. One ordinary photo reuses its cached original when metadata supplies the cache key; other requests use the item-download endpoint. A multi-item response is a ZIP (trailer checked), unzipped into staging on the destination volume and renamed into place, never overwriting or appearing half-populated. Selections are resolved by `SelectionDownloadResolver` (selected pages only, two at a time, verified slots, unchanged fingerprint). Incoming-album downloads require a current verified download grant and use the album reference; they never reuse personal cached originals.

**Drag-out** writes one `NSFilePromiseProvider` per promised item (each loaded still with a distinct name, else one folder) sharing a `PhotoPromiseBatch`. Each request creates a `PromisePlaceholder` with a cancellable file `Progress`; the first downloads everything once, extracts into staging on the destination volume and matches files by name, unzipping nested Live Photo archives. An item replaces its placeholder only while unchanged, else is placed exclusively. Text rides along when every item is loaded.

**Copy** places only the `filename,id` text: Finder and Photos ignore pasted file promises, and lazily provided file URLs are read at copy time by clipboard managers. **External editor handoff** reuses the original pipeline, always opens a separate collision-safe copy under Documents and never writes edits back.

**Range warming.** `ThumbnailRangeDownloader` reads one metadata page and runs two low-priority thumbnail workers at a time for a day range through the shared jobs and cache, within the budget. `ThumbnailPreloadModel` saves the request per namespace in defaults, resumes it after load once timelines are verified (also after the library changes mid-run), suspends on account switch and reports through an Activity entry whose Cancel asks for confirmation.

## Mutations and selection actions

All of these resolve a verified selection first (invariant 5) and finish with an authoritative read (invariant 6).

- **Favorites.** Optimistic: a per-space pending overlay is broadcast before the NAS call and only confirmed chunks patch the canonical field. `setFavoritesBatch` claims IDs against the pending set, writes chunks of 100 in order, keeps completed chunks on failure, rolls back failed and unsent IDs and schedules one coalesced Favorites refresh; the viewer's single-item path wraps it. An all-favorite selection unfavorites; a mixed one favorites the rest.
- **Ratings and tags.** Canonical fields requested with every page and Diff lookup. Not optimistic: writes go in chunks of 100, claim the items, and are followed by an authoritative `Browse.Item get`; only rating and tags are replaced in stored details, the affected tag indexes are withdrawn, and an annotation change is published to browser windows and viewers of the same scope. A tag is created, then added. Tag filtering compares folded names, not one space's tag IDs.
- **Rotation.** Normal rotation publishes an optimistic quarter-turn, sends `Browse.Item.set`, applies field-scoped authoritative values and restores presentation on failure; the viewer applies only the delta between EXIF orientation and Synology's `orientation`. Thumbnail-only rotation and repair are a separate cancellable stream, one item at a time: download the three renditions, rotate, `set_regenerating`, upload, poll for the new cache key. Repair turns only if `sm`, `m` and `xl` agree confidently. Ambiguous failure or cancellation runs `restore_from_regenerating` and a reread, adopting an advanced cache key.
- **Deletion.** `BackgroundTask.File delete`, polled via `BackgroundTask.Info get_status`; because `done` does not name deleted items, the IDs are read back (remaining items mean "not deleted", an unreadable result means unconfirmed). Every outcome runs the same reconciliation: Personal Diff, removal of confirmed IDs from index and details, revalidation of catalogs and summaries, and the metadata-invalidation reset scope. One deletion runs at a time.
- **Upload.** Finder drops upload sequentially with progress to the timeline, the open Personal folder or an owned album. The affected collections are invalidated before and after, and the refresh runs even after an uncertain result. The NAS indexes and generates thumbnails asynchronously, so the upload manager polls the uploaded IDs at 3, 5, 10, 20 and 30 seconds and refreshes again once every thumbnail is ready. Each poll ends when the browser that started it disappears or the session ends.
- **Refresh.** `refreshMetadata()` forces each space's Diff reconcile (Shared only once it has a cursor), then withdraws only this run's validation of catalogs and album, folder and summary lists; `LibraryModel` restarts the album and opened-collection streams, which emit cached values first and publish only changed snapshots.

Writes from the UI queue through `LibraryModel` (favorite writes in order, album writes through `serializedAlbumWrite`) so none hits the repository's busy rejection.

## Albums and sharing

An owned normal album keeps its identity when shared; sharing is an attribute of that album and separate from Shared Space. The album list is loaded on demand (by the Albums destination or a pinned row) and an album's metadata when it is opened or downloaded; neither is polled.

**Namespaces.** Owned mixed albums use an album-scoped metadata namespace with contextual details, thumbnails and stills. Each incoming album has its own namespace and thumbnail scope, so owner item IDs never collide with Personal Space or other albums; derived filters keep that scope. The repository stores incoming summaries without sharing references and keeps references and effective capabilities in memory after a fresh list read. Cached incoming rows stay visible offline but grant no network or mutation authority. Incoming metadata is excluded from the personal inventory and Map.

**Member origin.** Album members may come from either space, and neither item IDs nor `owner_user_id` reveal which. For an album action the repository reads fresh album details and both spaces' `Item get` in batches of 100, and requires ID, owner evidence, capture time, type, Live Photo type, filename, size and thumbnail unit/revision to match exactly one space; both, neither, a restricted space or a mixed batch fail before any write or bulk download. Probe reads are never stored in space namespaces. Verified homogeneous selections route favorites, rotation, downloads and editor handoff (Personal only) through the resolved space; only verified Personal selections can be contributed to albums. Album mutation events stay album-scoped.

**Mutation lifecycle.** Owner album writes serialize through a `MutationLane` and invalidate album-list validation and the collection's membership before and after, fencing admitted reads even without count changes; cached data stays as unverified, dependent filters are dropped, library items are untouched. Commands capture the timeline, ordinals, known IDs and authority, then resolve only the selected pages with leased registrations. Additions send only IDs missing from a verified destination. Rename checks ownership, type and result; deletion fences reads and verifies absence. `CollectionCapabilities` gates menus and drags; actions still verify when they run.

**Sharing writes.** The sharing sheet demands a fresh album and current Photos identity, verifies ownership, and sends explicit changes using DSM principal IDs. Activation and grant updates are separate requests, so partial success is reported; readback confirms the result and unrelated named grants stay untouched. A sharing-only refresh invalidates album summaries, not photo membership. Password intent distinguishes omission, a new value and an empty-string clear; expiry is optional epoch seconds (0 clears), and selected dates use the end of the local day. Recipient avatars are coalesced and bounded, and a Photos ID plus DSM UID pair is checked before a relative profile-photo descriptor is resolved against the configured NAS.

**Presentation.** `AlbumPresentationStore`, keyed by account namespace, persists ordered pinned album IDs, never metadata. Pins demand cached-first summaries; only a complete verified list removes missing pins and the restored route. An opened album's header occupies document space before photo days and is part of `LibraryViewportGeometry`. Browser drags carry an opaque in-process selection handle beside any file promise; cards and pins consume it once, re-verify account and target, and resolve it through the shared verifier. Album drag-out carries a folder promise and an in-process album nonce, so pin reordering never resolves membership.

## Locations and Map

Pages carry optional `additional.gps`, so coordinates need no extra request. Map reads a compact `item_index` projection per space namespace. A complete inventory lists located and unlocated IDs; row profile, epoch and persisted completeness gate its authority. Once a space's Diff has applied this run, a complete stored inventory is current without a scan and Diff changes update it. Otherwise one coalesced engine-owned scan runs after reconciling (Personal: 1,000-row scoped reads with staged uniqueness, per-day counts and a terminal fence; Shared: catalog, planner and `.locations` batches, then an empty Shared Diff before one atomic replacement that commits the cursor). The last subscriber leaving cancels a Shared scan without a partial commit. A failed scan keeps previous pins; cached pins stay visible and verification retries after a backoff or when the network returns.

`MapClusterBuilder` is a deterministic radius clusterer (newest-first, joining the nearest open cluster within one radius on both axes) whose radius doubles until at most 64 annotations remain; `MapBrowserModel` reclusters off the main actor after camera changes with a short debounce. Opening a pin or cluster passes the selected IDs and a space-bearing location revision to the repository, which validates membership and registers a session-only `.mapFilter(UUID)` collection on the common pager; its sparse slots materialize from canonical details of the source space, with registration and revision rechecked after every suspension. Projection changes invalidate dependent registrations and return to the preserved Map camera. Session filters are never restored after launch. Location labels are not implemented.

## App shell, navigation and Info panel

`AccountController` owns the open `AccountContext` (the account's `AppSession`, `LibraryModel`, navigation, Info, filter, preload and sync models). In development builds a `.env` file wins; otherwise `AccountStore` lists accounts in defaults with each password and device token in one Keychain item, read once per open. Switching ends the context (models cancel tasks, `AppSession.end()`, then `CachedPhotosRepository.shutdown()`, which admits no further work and logs out) and builds a new one; views and auxiliary windows are keyed by context ID. `SignInModel` verifies a sign-in with a short-lived client before storing it; the new context loads behind the setup pages (`AccountController.setupStep`). Signing out deletes the cache directory (`CacheInventory.remove`); `CacheInventory.scan` reads every cache database read-only for usage by category and its `account.json` label, written when a repository opens.

Startup loads cached-first Personal Library and Favorites concurrently. `AppPreferences` declares every persisted preference. `LibraryModel` (workflow extensions for rotation, favorites, deletion, annotation and albums) holds timelines, albums and command routing, with the repository as a tracked property set by `load()`.

`AppSession` also owns the account's `ActivityCenter`, download and upload managers and `LocalDragRegistry` (drag handles and running drag sources). `end()` cancels transfers, file promises and upload polls, drops drag handles and settles running activities as cancelled without cancel or retry closures; the managers then refuse work, so a late file promise fails.

The shell is a `NavigationSplitView` with eight destinations (Library, Favorites, Recently Added, People, Subjects, Tags, Map, Albums) plus pinned albums; changing destination closes the viewer. The unified toolbar overlays the detail column; the viewer fits below it and a magnified photo may extend behind it. `NavigationModel` is the single source of navigation state and persists one version-10 payload on every change: the selected destination and space, the last opened album identity, per-space folder mode/path and opened People/Subjects/Tags entries (namespace-fenced), and per-collection timeline anchors (item ID, ISO day fallback, offset, server page-offset hint). Restoration opens the nearest day, then refines to the photo once its page loads; a restored album is cleared only when a verified album list lacks it. Anchors are saved without notifying observers. Any other payload version is discarded. Map filters are not persisted.

The Info panel is a floating utility window. For a multi-item selection `InfoPanelModel` shows a synchronous count and day range, then a debounced `SelectionInfoResolver` computes exact size and media counts from only the selected sections, leaving the size unavailable if any item lacks a filesize; it follows the viewer's current item and does no page reads while hidden. Pages bundle `exif` and the Personal folder path with the existing `additional` fields so single-item details need no extra request.

## Activity and diagnostics

`ActivityCenter` is a main-actor model owned by `AppSession`; `PhotoCache` does not know it. Work that changes the NAS or transfers data calls `begin` with a typed `ActivityKind` and settles the handle with `succeed`, `fail` or `cancelled`. Succeeded changes leave the tab at once, transfers stay until dismissed, failures keep their items and a retry closure and open the popover at most once per 10 seconds. History merges adjacent succeeded counted changes of one kind within 60 seconds and keeps 500 records; the tab keeps 200 settled entries. A newer favorite or rating clears that photo from older failures. The connection state derives from authentication status, the Personal Library error and the last Refresh failure; `noteConnectionState()` posts lost/restored notices and sets `connectionIsHealthy`. Failure details keep only error type names and codes, and copied reports scrub session, token and credential values.

`RepositoryError` classifies failures as server, busy, stale, unavailable, invalid input, unconfirmed or unexpected, and `ResourceEvent.failure` carries it. `RepositoryError.record` logs every failure the repository streams or the app shows: unconfirmed writes, malformed responses, unknown API codes and broken invariants go to the `unexpected` category as errors; ordinary offline, busy and stale failures go to `failures` at info level. Server text stays private. Session IDs and tokens are URL query items, so errors are logged as `\(error.logSummary, privacy: .public)` (type, domain, code, scrubbed message; never `userInfo` or `String(describing: error)`), free text goes through `LogRedaction.scrub`, and credential types redact their `description`. The log subsystem is the bundle ID, with categories for viewer assets, originals, video (repository, transport, player), rotations, decoding, folders and `repository.diff`. The Diff category records each applied interval as counts, each reset or disabled feed with its cause, the stored inventory state at launch, every transition of a complete inventory to incomplete with its writer, and each Map scan's cause and outcome.

## Build modes

`scripts/run.sh` assembles the bundle (`io.github.finia2na.cirrusphotos`, executable `CirrusPhotos`) with `Sparkle.framework` in `Contents/Frameworks`, signed inside-out with the self-signed "Cirrus Photos" certificate (`scripts/signing.sh`; development builds fall back to ad hoc, distribution builds require it) and no entitlements (`make profile` adds `get-task-allow` to the development bundle). The version exists only in `scripts/version.env`; `Resources/ThirdPartyNotices.json` is copied into the bundle and drives Settings ▸ About. Development builds (the default, `--release`) read a `.env` beside the checkout or bundle, keep the cache in the repository's ignored `.cache/` (`CacheLocation` finds it by `Package.swift`, since LaunchServices gives no dependable working directory) and get the `.env` host's ATS exception. Preferences and Keychain items are keyed by the bundle ID.

`--distribution` builds an optimized bundle in `.build/distribution/` with `-DCIRRUS_DISTRIBUTION`: `CredentialStore.environmentFile()` is compiled out, the cache root is `~/Library/Application Support/io.github.finia2na.cirrusphotos/`, there is no ATS exception, and `SoftwareUpdater` starts Sparkle against the website's appcast (`SUFeedURL`, `SUPublicEDKey`) with **Check for Updates…**. Development builds link Sparkle but never start it. `scripts/release.sh` builds the DMG and its signed appcast item.

## Testing
