# Architecture

This document is the source of truth for current technical structure, subsystem boundaries, data flow and invariants. User-visible behavior is in [PROJECT.md](PROJECT.md); server request shapes are in [SYNOLOGY_PHOTOS_API.md](SYNOLOGY_PHOTOS_API.md); how that API behavior was established is in [capturefindings](capturefindings/README.md). Keep each section short and name a type only when it is an entry point to the code.

## Overview

| Module | Role |
| --- | --- |
| `TimelineCore` | Platform-independent models and geometry: day navigator, fixed photo grid, viewer transform and dismissal math, map clustering. |
| `SynologyAPI` | Wire and domain models, the `PhotosTransport` contract, the concrete authenticated `SynologyClient`, credentials, diagnostics. |
| `PhotoCache` | `CachedPhotosRepository` (the actor every consumer talks to), the metadata engine, GRDB-backed `DiskCache`, selection resolvers, `PhotoViewerSession`, `LibraryIndex`/`LibraryPageWindow` and the filter controller. |
| `CirrusPhotosApp` | The SwiftUI/AppKit executable (`CirrusPhotos`, built as the Cirrus Photos app bundle). |
| `TransportTestSupport` | Test-only `TestPhotosTransport` with a failing default for every request a test does not implement. |

Dependencies point downward in that order. The app creates one `CachedPhotosRepository` per signed-in account (`AppSession`) and the UI reaches the NAS only through it. SwiftUI hosts the shell; an AppKit viewport virtualizes the shared photo browser; AppKit/Core Animation draws the viewer canvas; AVFoundation plays repository-backed video ranges.

## Invariants

These hold across subsystems and are not obvious from any one file.

1. **Cached-first, NAS-authoritative.** Repository reads are finite typed `AsyncStream`s: the cached value first, the current value after validation, then finish. Cached reads never wait for login or a network slot. Cached metadata is provisional until validated, and stale content stays usable when validation fails (offline, slow, or a server error). Each resource is validated at most once per run; nothing polls for external changes. The manual Refresh withdraws only this run's validation; it never clears the cache.
2. **Fencing.** Every asynchronous metadata write carries a `MetadataWorkToken`: repository admission, storage and reset generations, job identity and the relevant mutation epochs. SQL admissions also bind the destination namespace and its revision/reset epoch. Transactions never suspend. A stale admitted write cannot overwrite newer confirmed fields; local mutation patches tolerate earlier local revisions but keep namespace and reset fencing.
3. **Diff feeds are the only cross-run freshness proof.** A terminal Diff v7 interval of at most 2,000 changed IDs and 4 MiB can advance the cursor together with replacements and deletions. A partial, oversized, malformed, unsupported or rejected interval invalidates coverage centrally and falls back to authoritative reads. No feature owns a cursor. Details in [Repository and metadata engine](#repository-and-metadata-engine).
4. **Nothing defaults to Personal Space.** Every transport, repository and app method that works in a space or collection takes it explicitly. Album items have no inferred origin space.
5. **Verified selections.** Actions on photos (favorite, rotate, tag, rate, delete, download, add to album, edit) run on a selection resolved by one verifier that proves membership by ordered IDs, fingerprint and item identity. A changed fingerprint, identity or membership replacement fails the action instead of acting on different photos.
6. **Writes end in a read.** Every NAS change is followed by an authoritative read of what it touched, even after failure or cancellation. An uncertain outcome is reported as `unconfirmed`. Creation is never retried automatically. Only one write runs per `MutationLane`; a second fails with `RepositoryError.busy`.
7. **Capture-local time.** `PhotoItem.time` is a capture-local wall clock encoded as epoch-shaped seconds, not an instant. Grouping and formatting use GMT calendar components so 21:00 displays as 21:00 on any Mac. No timezone is inferred from location or device.
8. **Pre-1.0 formats are disposable.** Incompatible preferences, navigation state and cache schemas are discarded and recreated; metadata formats are discarded without decoding. Media bytes keep their format.
9. **Logs hold no secrets.** Diagnostics exclude filenames, cache keys, credentials, tokens, session IDs, cookies, authenticated URLs and response bodies. Sharing references are never persisted in album summaries.

## Transport

`PhotosTransport` is the repository's only dependency on the NAS: login, collection-aware timelines and pages, scoped indexes and folders, albums and sharing, favorite/rating/tag/rotation/deletion writes, uploads, thumbnails, originals, downloads, video ranges and the Diff feeds. `SynologyClient` implements it. Every JSON Web API call goes through one `request`/`call` path that adds the session and maps envelope errors; the client chooses the `Foto` or `FotoTeam` variant of an API from the space (`SynologyClient.api(_:_:)`). Large transfers (originals, uploads, downloads, video ranges) use delegates that report byte progress, treat request timeouts as inactivity limits, and read the session through one accessor. Responses are bounded (for example the Diff response limit).

**Sign-in.** `SynologyCredentials` carry a `SecondFactor` (none, `.env` TOTP secret, typed code, trusted-device token) and a `ServerTrust`. Login uses the web client's `webui` session and device name "Cirrus Photos"; a typed code also requests a device token (`did`), and later logins send it as `device_id` instead of a code. DSM's 403 becomes `secondFactorRequired`. The client keeps renewal credentials (a typed code is replaced by its token) and renews once per expired session (106, 107, 119) for every JSON call, then retries; a failed renewal is reported through `onSessionRenewalFailure`. The repository maps rejected credentials, codes and certificates to `AuthenticationStatus.needsSignIn`; other rejections stay failed until retried, and unreachability retries on the next request.

**Transport security.** `CirrusTrustDelegate` applies the policy to the NAS host only: system validation, else a pinned leaf SHA-256 the user accepted, reported as `untrustedCertificate` when refused. The repository turns that into `AuthenticationStatus.untrustedCertificate`, and `AccountController` asks before connecting; accepting pins the fingerprint on the stored account, or per host in defaults for `.env` accounts. `run.sh` writes an ATS exception only for the `.env` host. The session uses ephemeral cookie storage.

Request shapes, versions and what each was verified against are in the API reference, not here.

## Identity and scopes

`PhotoSpace` is Personal or Shared. `PhotoContentScope` is either a space or an unresolved album authority (an owned album ID, or an incoming album's owner and album IDs). `PhotoItemIdentity` pairs a scope with an item ID. Unit IDs are separate media-resource identities. `owner_user_id` is kept as server evidence but never used as an origin discriminator.

`PhotoCollectionDescriptor` identifies a collection: Library, Favorites, Folder, Person, Subject and Tag carry their space; Album descriptors keep contextual authority and expose no inferred space; Map and filter descriptors carry their source space or scope and registration rejects a mismatch. `MetadataNamespace` requires an explicit scope; `CollectionKey` combines it with the descriptor. The normalized tables, page and thumbnail keys, original and video resources, mutation events and observer streams are all scoped, so Shared Space, Personal Space, each owned album and each incoming album have isolated metadata, media and mutation authority. Media transport rejects a scope it does not support before sending a personal request.

Shared Space reconciles its own Diff feed and keeps its own inventories, favorite overrides, pending writes and refresh jobs. Personal mutation and invalidation broadcasts never touch shared pages. Space selection persists separately from the destination. Which Shared Space endpoints are captured and which are inferred is listed in the API reference.

## Repository and metadata engine

`CachedPhotosRepository` is the sole coordination actor. State is split into owned structs (authentication, `MetadataEngineState`, image work, favorites, item mutations); actor-isolated extensions hold the authentication, metadata, media, favorites and rotation pipelines so suspension points and ordering stay on one actor. `isAdmitted(_:)`/`requireAdmission(_:)` are the single admission-epoch check.

**Layout.** A day catalog (`CollectionDayCatalog`) validates NAS Timeline sections into unique capture-local days and counts. `CollectionDayPager` emits one logical page per day with capacity 250; `DayPageAddress` is collection, day, day-local offset, capacity and order, and excludes section index, count and fingerprint. Catalog revisions and per-day membership generations are independent: inserting an unrelated day keeps older slots, while any change inside a day invalidates that day's membership. Albums yield the same catalog from an item scan, because the Timeline endpoint ignores `album_id`.

**Tables.** Identity/time/GPS projection (`item_index`), canonical details with annotation authority (`item_details`), catalogs and day generations, exact ordered `day_pages` and reverse `page_items`, plus summaries. Evicting a detail leaves every known ID and ordinal in place, so a page is a list of exact slots that may be unloaded. `PhotoPageSnapshot` carries membership verification and per-slot details; per-slot verification governs media and actions.

**Reads.** `MetadataReadPlanner` batches up to 1,000 contiguous demanded items across at most 32 days with no gap padding, and the engine keeps two physical network slots. Detail jobs are keyed by `PhotoItemIdentity` so consumers share work, cancellation and priority promotion without joining distinct scopes. A coverage mismatch joins one collection recovery and gets one retry. Album actions request fresh contextual details, which supersede older in-flight authority.

**Diff reconciliation.** Each space has its own feed (`Browse.Diff` v7 `get_version`/`list`, independent cursors, `MetadataSourceState`). Modified IDs are looked up in batches of 100 and fenced; an empty interval commits only the cursor. `item.merge` lists bare IDs (a Live Photo's short-lived video item folded into its still): merged IDs are looked up with the modifications, present means replacement, absent means deletion. Because that meaning is inferred, an interval with merges compares a complete inventory with the day-catalog count and resets on mismatch. `item.move`, `similar`, non-integer merges and unknown user events recover through authoritative reads. The favorite-event feed (`list_user_event`) is read after the item feed from the same cursor, so the committed cursor never skips a favorite event; any other event type recovers.

**Proof run.** A successful reconciliation records `metadata_state.proof_run`. A cached page then counts as verified without a read when it was stored under the current reset epoch, its day generation and count match, its collection's catalog was validated this run, and the collection is a Library, folder or general tag (either space) or Personal Favorites. Cached details are verified under the same proof. A changed ID with no index row invalidates the days of the cached pages that list it. The same reconciliation validates untouched folder catalogs for this run without a read: a folder qualifies when it was validated in an earlier run under the current reset epoch, its stored pages list every member, and no changed or deleted item was or is in it (previous folders from the folder pages that list the item, current ones from the replacement's `folder_id`; a replacement without one disables the shortcut). An unshared owned album is proven too: its catalog row records the album `version` (from the album list validated this run, observed before the read) under which the catalog and all its pages were stored, and a later run with an unchanged version validates the catalog without reading it. Its album-context detail copies are proven when Personal is proven this run (and Shared, when the account has a Shared feed), because each space reconciliation marks album copies of every changed, deleted or favorite-event ID stale and advances those album namespaces' revisions, and album reads wait for those reconciliations. Like Shared Library details, copies of Shared Space members can miss favorite changes made elsewhere, since Shared Space has no favorite feed. Shared albums, People, Subjects, Recently Added, incoming albums and Shared Favorites always use current-run reads.

**Background work.** `MetadataSyncModel` starts when Personal Library and Favorites timelines are verified. It and the timeline-section warmer re-check their start conditions through Observation tracking, so every `LibraryModel` property those checks read, including `repository`, must be tracked; a guard that returns on an untracked read never runs again. It walks the same targets as the warmer (plus owned albums and each space's folder tree) through the cached-first page path at prefetch priority, so Diff-proven pages finish without a request. The current source collection goes first and preempts the target in progress. An incomplete pass repeats after 30 seconds doubling to 10 minutes, or when `NWPathMonitor` reports the network again. Each running pass holds an `ActivityKind.metadataSync` entry with no cancel action; its status is updated at most once a second and it is discarded, not settled, when the pass ends, so it never enters History. The "Load All Timeline Sections" warmer (`TimelineSectionCacheLoader`) runs the same engine with a 64-page lookahead; its default forces authoritative membership.

**Filtering.** A metadata filter is a session-only collection derived from a source (Library, Favorites, an album, a folder or a Map result). `LibraryFilterController` reads the scalar facet columns stored on `item_details` (including a folded filename key) for the whole source in one database read and applies normal page verification, so filtering and filename search work offline from cached data. Map and filter-derived sources read cached pages through the network-disabled path in batches of 64. The controller has no scan of its own: it observes page commits (coalesced, bounded wakeups that carry no payloads) and indexes whatever any consumer stored, then rereads the facets when the source becomes verified. A `.libraryFilter(UUID)` registration keeps the exact ordered IDs and source references; source verification gates each derived slot, and source invalidation withdraws membership authority. Camera/lens/extension suggestions are cached per account and collection and merged, never discarded, when coverage is incomplete. Derived collections have no array cache of their own.

**Collection indexes and folders.** People, Subjects and Tags share one kind/entry type from transport to storage. Index and folder-directory jobs are keyed by space, share the cached-first admission and subscriber lifecycle, persist complete listings per namespace, and keep the previous listing when a read fails. Person IDs, concept IDs and tag IDs are ordinary collection descriptors served by the common engine. A folder directory is the folder's summary plus a paged `Browse.Folder list` of its children; the root resolves its own ID with `get`, and the background sync passes each child the summary from a parent listing verified this run, so a tree walk costs one listing per folder. Listings are still read once per run: no Diff feed reports folder creation, renames or removal, and folder records carry no version. Folder covers are derived from cached directories and first pages, stored in `folder_covers` and recomputed once per run. Recently Added groups by the server's `indexed_time` day (not capture time) and fails closed when that time is missing or inconsistent.

## Cache

`DiskCache` owns a GRDB `DatabaseQueue` (WAL, `synchronous=NORMAL`). `CacheSchema.swift` declares every table as a Codable record; nested values are JSON text; storage code uses the query interface, not hand-written SQL ([decision 002](decisions/002-grdb-records.md)). Storage methods are synchronous so no transaction suspends. Compressed images and video segments are hashed files under an account-scoped directory inside the repository's ignored `.cache/` directory; `CacheLocation` finds the repository by `Package.swift` because LaunchServices gives no dependable working directory ([decision 001](decisions/001-development-cache-location.md); changes with #84). The index has an explicit schema version; an incompatible or unreadable index and its media files are recreated from NAS data. Rows record validation run, access time, ETag, Last-Modified, content digest and a monotonic revision.

**Reset scopes.** A metadata-only clear advances the storage generation at admission, removes metadata rows transactionally, broadcasts an invalidation revision only on success, and preserves media and transfers already admitted. Full clear also advances the whole-cache generation, removes media and cancels media work. Deleting items uses the metadata-invalidation scope too, so the UI reloads as after a metadata clear.

**Budget.** Every normalized write enforces the shared budget after commit. Eviction removes video segments first, then viewer previews, full images, thumbnails, canonical details and membership, compact inventory and finally catalog metadata; evicting the compact index clears persisted inventory completeness. The usage figure is an in-memory estimate: media writes adjust it exactly and metadata growth is re-measured by a full scan at most every 15 seconds. Budgets of 200 MB or more keep a reserve below the limit; smaller budgets scan on every write. Read recency is batched and flushed before eviction. The budget and the Settings "Stored data" figure count media payload bytes plus stored metadata column lengths; they exclude SQLite free pages, indexes, WAL/SHM, filesystem block rounding and temporary files, so the directory on disk is a few percent larger (about 4% on a measured 12 GB cache). Metadata eviction subtracts the same column lengths the scan sums, so the estimate matches a fresh scan.

**Validators.** Original GETs send `If-None-Match`/`If-Modified-Since` when validators are cached and accept `304` only with local bytes. Thumbnails are versioned by the NAS `cache_key`, which is part of the cache identity: an exact cached thumbnail is current once its descriptor comes from metadata verified this run, so thumbnails are fetched only on a cache miss and send no validators. Preview and ordinary `xl` thumbnails share a key and file; ordinary demand promotes the category and preview work cannot demote it.

## Browser

One virtualized browser serves Library, Favorites, folders, People/Subjects/Tags results, Recently Added, opened albums and filtered or Map results.

**Data flow.** The repository publishes day-grouped page snapshots with stable day-local sections. `LibraryIndex` hashes the ordered descriptor snapshot and maps each UTC day to exact slices of the contributing section responses, with page-local, day-local and collection-ordinal coordinates, fixed-grid visual rows and directional destinations across day breaks. `LibraryViewportGeometry` derives document height and square slot positions from descriptor counts and the 3–10 column preference before any metadata loads; only the interaction rectangle (aspect-fitted frame or full square) depends on loaded items, and it never moves slots. Distant slices keep scalar geometry only. `LibraryPageWindow` keeps all viewport-demanded pages plus prefetch up to eight, emits cached pages promptly and rejects obsolete responses. Windows rebase by address and retire in-memory proofs on typed day invalidation even if counts are unchanged.

**AppKit viewport.** An `NSScrollView` hosts a flipped document that creates date headings and pooled layer-backed `BrowserPhotoCellView`s only for the visible region plus overscan; the cell is the keyboard focus, accessibility element and viewer-transition source while pointer input passes through to the document. A cell shows cached bytes first, validates after current page metadata arrives, keeps a displayed rendition visible while validating, and loads off the main thread with cancellation on reuse. An AppKit overlay draws selection outlines and marquee feedback. Scroll position is restored by visible item ID plus pixel offset, else by date and slice. `BrowserScrollIntentCoordinator` owns a single typed restoration, preservation, reveal or selection-navigation intent; newer intents replace older ones and user scrolling cancels refinement.

**Limits.** Six thumbnail transfers and two metadata requests run concurrently (`NetworkGate`), visible demand before prefetch, with bounded queues; shared jobs cancel when their last subscriber leaves. ImageIO downsamples off the main actor through a gate of four concurrent decodes that runs the newest request first, and an `NSCache` bounds retained decoded images. `LibraryModel` uses Observation, and per-collection timeline state is announced through one revision coalesced to once a second during warming.

**Selection.** `LibrarySelection` is a session-local set of ordinal ranges per collection, so selecting a whole collection never materializes metadata. The key window's AppKit responder dispatches the same commands as the Library menu. Membership signatures invalidate an ordinal selection when order or membership changes. Selection survives recycling, scrolling, resizing and destination switches.

**Navigator.** The equal-day track gives each populated day the same fraction of the track, so pointer lookup is a constant-time index and some days cannot be targeted by pointer when days outnumber pixels; keyboard and accessibility actions step single days. User input creates a jump request with a fresh identity; scroll feedback updates the selected day without a jump. After an index change the nearest remaining older day is used.

## Viewer

`PhotoViewerSession` is the single actor for viewer coordination. It navigates an immutable `LibraryIndex` using section-prefix counts, keeps at most three metadata pages (`ViewerMetadataWindow`) and the current plus two adjacent encoded originals (`ViewerImageWork` owns bytes, tasks and shared cancellation). Selection generations on replayed snapshots and request tokens reject obsolete results during rapid navigation. Verified metadata preserves the selected item by ID when its page moves; provisional metadata may read cached images but cannot authorize downloads. A changed authoritative snapshot invalidates ordinary navigation with an explicit reopen state while the presentation keeps its decoded image; a missing selected detail keeps the displayed image. A Favorites viewer keeps its opening playlist while membership changes.

**Image policy.** The viewer shows the configured thumbnail immediately and reads cached `xl` previews and originals at once. Network `xl` and original requests start after the selection is stable for 100 ms, which avoids transfers for intermediate selections during key repeat; then they start concurrently and warm one adjacent `xl` in each direction. Two transfer slots allow one speculative request, and selecting an in-flight neighbor promotes its job. Neighbor originals are requested only after the current one succeeds and keep compressed bytes only; neighbor thumbnails and `xl` previews may be decoded ahead so cached navigation never shows a blank frame. An `xl` upgrade is kept if the original fails; a decoded original is final. An original that is neither cached nor fetchable is retried every two seconds until it arrives. `FullImageDecoder` decodes with ImageIO off the main actor, admits one decode plus one replaceable waiting request, and rejects images above 384 MB decoded.

**Canvas.** The AppKit canvas is layer-backed: a backdrop layer and an image layer whose contents are set only when the displayed image identity changes. Fit, zoom and pan come from `PhotoViewportTransform`; transitions animate only layer position, bounds and opacity, so no frame resamples the image, and retargeted transitions start from the presentation layer so nothing jumps. Three reusable layers (previous, current, next) carry the horizontal swipe; the dismissal gesture is handled inside the canvas (direction lock, translation/scale/backdrop response from `PhotoViewerDismissal`) and ends by calling the same close pipeline as Back/Escape, so cleanup happens once after the visual finishes. All of this is driven by one internal phase value rather than overlapping flags. Reduce Motion replaces spatial transitions with a fade. Opening comes from the thumbnail's window-space rectangle; closing resolves the live cell rectangle, with a timed fade if none exists.

**Status.** `ViewerStatus.make` combines the shown image tier, the session's full-image status, decoding, transfer progress, the stall flag and video playback status into the toolbar title text and progress. `ViewerStatusModel` is observed separately so progress does not redraw the viewer. Progress is network-only (`fullImageProgress` follows the shared transfer regardless of who started it), moves forward only, and a load with no data for 8 seconds is marked stalled.

**Inspection overlays.** The filmstrip reuses the browser's thumbnail geometry and the viewer's bounded metadata window. The histogram and the two GPU overlays (highlight peaking, focus edges) work on the displayed image off the main actor: `ViewerGPUImageRenderer` resamples to a bounded raster, runs an effect shader (an optional statistics pass for focus edges), and reads back a small overlay. Requests are serialized; cancelled work is discarded before publication; selection changes hide old overlays. Peaking marks rendered near-white pixels by a 5% HSV-saturation tolerance, which is a heuristic and not a raw-clipping detector.

## Media

**Thumbnails and originals.** Thumbnail, original, preview and video resources have semantic keys that include the account namespace, scope and revision. Thumbnail renditions follow the user setting; compatible fallback renditions stay visible until the selected one arrives. The viewer's handling of originals and previews is described above.

**Video.** `VideoQualityPreference` is a semantic choice, not a wire value; Automatic targets High. The effective rendition is the nearest advertised known quality (lower wins a tie), Original is a separate stored-file variant and the fallback when nothing converted is advertised. The repository serves cached 64 KiB segments first and groups contiguous missing demand into HTTP windows of at most 1 MiB on a separate two-transfer lane. A shared window replays received bytes to concurrent subscribers and stops when the last one leaves; each response is staged in memory and split into persisted segments only after validation. If cached and fetched ranges disagree on ETag, Last-Modified or length, every cached segment of that rendition is purged and the request fails as stale. There is no adjacent-video prefetch, and the current item's metadata must be verified before a new network range starts (cached ranges are readable without it). `VideoAssetLoader` translates AVFoundation requests to repository calls through an opaque custom-scheme URL, so credentials and NAS URLs never reach AVFoundation. The player is keyed by selection generation and rendition so stale work is not reused, and a failed converted playback falls back once to the scoped original.

**Live Photo motion.** Motion waits for the full still and verified metadata. An indicator click or Force Touch press looks up the item's `Browse.Unit` members on demand (never persisted, so it needs a connection), picks the converted rendition nearest High and streams it through the same range cache. Lookup is fenced by selection generation. In an owned album the member's space is first verified with the member-origin read used for item actions. Motion is suppressed when Synology's display orientation differs from the original's.

**Downloads and export.** `PhotoDownloadManager` runs independent cancellable jobs; the client streams each response to a temporary file. One ordinary photo reuses its cached original when metadata supplies the cache key; other requests use the item-download endpoint. A multi-item response is a ZIP (trailer checked), unzipped into staging on the destination volume and renamed into place, never overwriting or appearing half-populated. Selections are resolved by `SelectionDownloadResolver` (selected pages only, two at a time, verified slots, unchanged fingerprint). Incoming-album downloads require a current verified download grant and use the album reference; they never reuse personal cached originals.

**Drag-out** writes one `NSFilePromiseProvider` per promised item (one per loaded still with a distinct name, else one folder), sharing a `PhotoPromiseBatch` snapshot. Each request creates an empty `PromisePlaceholder` with a published cancellable file `Progress` (Finder's pie); the first downloads all items once, extracts them into staging on the destination volume and matches files by name, unzipping nested Live Photo archives. An item replaces its placeholder only while unchanged, else is placed exclusively. Text rides along when every item is loaded (`.string` is never lazy).

**Copy** places only the `filename,id` text: Finder and Photos ignore pasted file promises, and lazily provided file URLs are read at copy time by clipboard managers. **External editor handoff** reuses the original pipeline, always opens a separate collision-safe copy under Documents and never writes edits back.

**Range warming.** `ThumbnailRangeDownloader` fetches one metadata page and two low-priority thumbnail workers at a time for a chosen day range through the shared jobs and cache; it does not pin entries or exceed the budget.

## Mutations and selection actions

All of these resolve a verified selection first (invariant 5) and finish with an authoritative read (invariant 6).

- **Favorites.** Optimistic: a pending overlay is broadcast before the NAS call, and only confirmed chunks patch the canonical favorite field. `setFavoritesBatch` claims every ID against the pending set, writes fixed-size chunks (100) in order, keeps completed chunks on failure, rolls back only the failed and unsent IDs and schedules one coalesced Favorites refresh. The viewer's single-item path is a wrapper over the same entry point. Favorite overlays and pending sets are per space. An all-favorite selection unfavorites; a mixed one favorites the unfavorited items.
- **Ratings and tags.** Canonical fields requested with every page and Diff lookup. Not optimistic: writes go in chunks of 100, claim the items, and are followed by an authoritative `Browse.Item get`; only rating and tags are replaced in stored details, the affected tag indexes are withdrawn, and an annotation change is published to browser windows and viewers of the same scope. A tag is created, then added. Tag filtering compares folded names, not one space's tag IDs.
- **Rotation.** Normal rotation publishes an optimistic quarter-turn, sends `Browse.Item.set`, applies field-scoped authoritative values and restores presentation on failure. The viewer applies only the quarter-turn delta between the file's EXIF orientation and Synology's `orientation`. Thumbnail-only rotation and automatic repair are a separate cancellable stream: one item at a time, download the three ready renditions, rotate locally, `set_regenerating`, upload converted files, poll for the new cache key. Automatic repair applies a turn only if `sm`, `m` and `xl` independently and confidently agree. Any ambiguous failure or cancellation runs `restore_from_regenerating` and a cancellation-independent reread, adopting an advanced cache key before reporting.
- **Deletion.** `BackgroundTask.File delete`, polled via `BackgroundTask.Info get_status`; because `done` does not name deleted items, the IDs are read back (remaining items mean "not deleted", an unreadable result means unconfirmed). Every outcome runs the same reconciliation: Personal Diff, removal of confirmed IDs from index and details, revalidation of catalogs and summaries, and the metadata-invalidation reset scope. One deletion runs at a time.
- **Upload.** Finder drops upload sequentially with progress to the timeline, the open Personal folder or an owned album. The affected collections are invalidated before and after, and the refresh runs even after an uncertain result. The NAS indexes and generates thumbnails asynchronously, so the upload manager polls the uploaded IDs at 3, 5, 10, 20 and 30 seconds and refreshes again once every thumbnail is ready. Each poll ends when the browser that started it disappears or the session ends.
- **Refresh.** `refreshMetadata()` forces each space's Diff reconcile (Shared only once it has a cursor), then withdraws only this run's validation of catalogs and album, folder and summary lists; `LibraryModel` restarts the album and opened-collection streams, which emit cached values first and publish only changed snapshots.

Writes from the UI queue through `LibraryModel` (favorite writes in order, album writes through `serializedAlbumWrite`) so none hits the repository's busy rejection.

## Albums and sharing

An owned normal album keeps its identity when shared; sharing is an attribute of that album and separate from Shared Space. The album list is loaded on demand (by the Albums destination or a pinned row) and an album's metadata when it is opened or downloaded; neither is polled.

**Namespaces.** Owned mixed albums use an album-scoped metadata namespace with contextual details, thumbnails and stills. Each incoming album has its own namespace and thumbnail scope, so owner item IDs never collide with Personal Space or other albums; derived filters keep that scope. The repository stores incoming summaries without sharing references and keeps references and effective capabilities in memory after a fresh list read. Cached incoming rows stay visible offline but grant no network or mutation authority. Incoming metadata is excluded from the personal inventory and Map.

**Member origin.** Albums may contain members of either space, and neither item IDs nor `owner_user_id` identify a member's space. For an album item action the repository reads fresh album details and both spaces' `Item get` in batches of 100, and requires that ID, owner evidence, capture time, type, Live Photo type, filename, size and thumbnail unit/revision match exactly one space. Matching both or neither, a restricted space or a mixed-space batch fails before any write or bulk download. These probe reads are never stored in canonical space namespaces. Verified homogeneous selections get favorite, rotation and download routing through the resolved space; editor handoff resolves origin too and rejects Shared Space members. Only verified Personal selections can be contributed to an album or an incoming album. Album-local mutation events keep album scope separate from space events.

**Mutation lifecycle.** Owner-side album writes serialize through a `MutationLane` and invalidate the album-list validation and the affected collection's membership before and after the write, which fences admitted reads even when counts do not change. Cached data stays available as unverified; dependent filter registrations are dropped; canonical library items are untouched. Commands capture the displayed timeline, selection ordinals, known IDs and repository-issued authority, then resolve only the selected pages with derived registrations leased so dismissing the source does not cancel an accepted operation. Membership changes add only IDs missing from a verified destination. Rename verifies ownership and type and checks the resulting name. Deletion uses a confirmed ID array, fences list and membership reads and verifies the album's absence afterwards. `CollectionCapabilities` decides which actions, album actions and downloads a collection source offers, and gates the menus and drags; actions still verify when they run.

**Sharing writes.** The sharing sheet demands a fresh album and current Photos identity, verifies ownership, and sends explicit changes using DSM principal IDs. Activation and grant updates are separate requests, so partial success is reported; readback confirms the result and unrelated named grants stay untouched. A sharing-only refresh invalidates album summaries, not photo membership. Password intent distinguishes omission, a new value and an empty-string clear; expiry is optional epoch seconds (0 clears), and selected dates use the end of the local day. Recipient avatars are coalesced and bounded, and a Photos ID plus DSM UID pair is checked before a relative profile-photo descriptor is resolved against the configured NAS.

**Presentation.** `AlbumPresentationStore` (shared across windows, keyed by the account/server namespace) persists an ordered unique list of pinned album IDs, never album metadata. Pins demand cached-first summaries even if the overview was never opened; only a complete verified list reconciles missing pins and the restored route. The overview sections sort and expand independently. An opened album supplies a header (cover, dates, sharing) that occupies document space before photo days; `LibraryViewportGeometry` includes its origin in all photo coordinates. Browser drags carry an opaque in-process selection handle beside any file promise; album cards and pins consume it once, re-verify account and target, and resolve the captured collection through the shared verifier. Album drag-out carries both the folder promise and an opaque in-process album nonce (scoped to the namespace and session, removed when either ends) so sidebar pin reordering never resolves membership.

## Locations and Map

Pages carry optional `additional.gps`, so `PhotoItem.coordinate` and the Info panel's map need no extra request. Map reads a compact projection from `item_index` isolated by space namespace. A complete inventory includes located and unlocated IDs; row profile, epoch and persisted completeness jointly gate its authority. Once a space's Diff has been applied this run, a complete stored inventory is current without a scan, and Diff replacements and deletions update it. Otherwise one coalesced engine-owned scan runs after reconciling the central boundary (Personal: 1,000-row scoped reads with staged uniqueness and per-day counts and a terminal fence; Shared: `acquireCollectionCatalog`, `MetadataReadPlanner` and `.locations` item batches, then an empty Shared Diff from the reconciled cursor before one atomic replacement that commits that cursor). Shared scan subscribers coalesce, and the last one leaving cancels the scan and prevents a partial commit. A failed scan leaves the previous pins available; cached pins stay visible when verification fails and verification retries after a backoff or when the network returns.

`MapClusterBuilder` is a deterministic radius clusterer (newest-first, joining the nearest open cluster within one radius on both axes) whose radius doubles until at most 64 annotations remain; `MapBrowserModel` reclusters off the main actor after camera changes with a short debounce. Opening a pin or cluster passes the selected IDs and a space-bearing location revision to the repository, which validates membership and registers a session-only `.mapFilter(UUID)` collection on the common pager; its sparse slots materialize from canonical details of the source space, with registration and revision rechecked after every suspension. Projection changes invalidate dependent registrations and return to the preserved Map camera. Session filters are never restored after launch. Location labels are not implemented.

## App shell, navigation and Info panel

`AccountController` owns the open `AccountContext`: the account's `AppSession`, `LibraryModel`, navigation, Info, filter, preload and sync models. A `.env` file wins; otherwise `AccountStore` lists accounts in defaults and keeps passwords and device tokens in the Keychain. Switching ends the context (models cancel their tasks, `AppSession.end()`, then `CachedPhotosRepository.shutdown()`, which admits no further work and logs out) and builds a new one; views and auxiliary windows are keyed by the context ID. `SignInModel` verifies a sign-in with a short-lived client before it is stored; the new context then loads behind the setup pages (`AccountController.setupStep`), and a download chosen there configures and starts the context's loaders before the shell exists. `AppSession` creates the repository through a factory. Startup opens the repository and loads cached-first Personal Library and Favorites concurrently. `AppPreferences` declares every persisted preference and key. `LibraryModel` (with rotation, favorites, deletion, annotation and album workflows in extension files) holds collection timelines, albums and command routing; it keeps the opened repository as a tracked property set by `load()`.

The session also owns the account's `ActivityCenter`, download and upload managers and `LocalDragRegistry` (drag handles and running drag sources). `end()` cancels transfers, file promises and upload polls, drops drag handles and settles running activities as cancelled without cancel or retry closures; the managers then refuse work, so a late file promise fails.

The shell is a `NavigationSplitView` with eight destinations (Library, Favorites, Recently Added, People, Subjects, Tags, Map, Albums) plus pinned albums; changing destination closes the viewer. The unified toolbar overlays the detail column; the viewer fits below it and a magnified photo may extend behind it. `NavigationModel` is the single source of navigation state and persists one version-10 payload on every change: the selected destination and space, the last opened album identity, per-space folder mode/path and opened People/Subjects/Tags entries (namespace-fenced), and per-collection timeline anchors (item ID, ISO day fallback, offset, server page-offset hint). Restoration opens the nearest day, then refines to the photo once its page loads; a restored album is cleared only after a verified album list lacks it. Anchors are saved without notifying observers. Any other payload version is discarded. Map filters are not persisted.

The Info panel is a floating utility window. For a multi-item selection `InfoPanelModel` shows a synchronous count and day range, then a debounced `SelectionInfoResolver` computes exact size and media counts from only the selected sections, leaving the size unavailable if any item lacks a filesize; it follows the viewer's current item and does no page reads while hidden. Pages bundle `exif` and the Personal folder path with the existing `additional` fields so single-item details need no extra request.

## Activity and diagnostics

`ActivityCenter` is a main-actor model owned by `AppSession`; `PhotoCache` does not know it. Work that changes the NAS or transfers data calls `begin` with a typed `ActivityKind` and its items and settles the handle with `succeed`, `fail` or `cancelled`. Succeeded changes leave the Activity tab at once, transfers stay until dismissed, and failures keep their items and a retry closure and open the popover at most once per 10 seconds. History appends on settle, merges adjacent succeeded counted changes of one kind within 60 seconds and keeps 500 records; the tab keeps 200 settled entries. A newer favorite or rating clears that photo from older failures. The toolbar's connection state derives from authentication status, the Personal Library error and the last Refresh failure; `noteConnectionState()` posts lost/restored notices and sets `connectionIsHealthy`, which the viewer checks before reporting a failed full-resolution load. Failure details keep only the type names and codes of the error chain, and the copied report scrubs session, token and credential values.

`RepositoryError` classifies failures as server, busy, stale, unavailable, invalid input, unconfirmed or unexpected, and `ResourceEvent.failure` carries it. `RepositoryError.record` logs every failure the repository streams or the app shows: unconfirmed writes, malformed responses, unknown API codes and broken invariants go to the `unexpected` category as errors; ordinary offline, busy and stale failures go to `failures` at info level. Server text stays private. Logging uses the `de.richardhanss.cirrus-photos` subsystem with categories for viewer assets, originals, video (repository, transport, player), rotations, decoding, folders and `repository.diff`. The Diff category records each applied interval as counts, each reset or disabled feed with its cause, the stored inventory state at launch, every transition of a complete inventory to incomplete with its writer, and each Map scan's cause and outcome. `make debug` opens Console and runs the app in the foreground.
