# Map-only Diff cache validation

Status: non-proof infrastructure implemented on 2026-10-09: strict bounded Diff transport/decoding, conservative pure location merge, shared metadata lifecycle/reset, repository-owned Map-filter dependencies, and cache-only filtered-page delivery. Production Diff validation is intentionally disabled because the mandatory large-interval completeness, cursor reset/rejection, feed visibility delay, positional-scan completeness/stable equal-time ordering, and Personal Space access-change evidence gates remain open. Map retains the conservative fingerprint path and stores no cursor/proof until every gate passes.

## Startup scan investigation (2026-10-25)

The reported `Scanning locations… 39,000 of 57,827` status comes from real network enumeration, not local cache parsing. `LocationIndex.locationIndex()` emits cached pins, awaits the verified Personal timeline, and skips enumeration only when its descriptor fingerprint equals the persisted location payload's fingerprint. Any changed day count or section geometry forces a whole-library scan, including changes involving only unlocated items. Conversely, GPS/thumbnail edits that preserve timeline geometry are not detected by this shortcut.

A read-only inspection of the current checkout's SQLite cache found one current-schema location payload: 57,827 scanned items, 26,612 located records, about 5.4 MB. Its source fingerprint matches a stored timeline containing 57,827 items. This establishes successful persistence at inspection time, not why an earlier launch scanned or whether the next authoritative timeline will match. All 11 `LocationIndexTests` pass, including cross-repository reuse and Map-before-Library startup. No live NAS requests or writes were performed for this investigation.

Before attributing every startup scan to required invalidation, reproduce two launches with no intentional library changes and add aggregate decision diagnostics in `LocationIndex.swift`: cache hit/miss/decode/schema outcome, fingerprint match/mismatch, scan start reason, scan duration, and `commitMetadata` outcome (currently swallowed through `try?`). Do not log payloads, IDs, coordinates, credentials, raw cursors, or authenticated URLs. Verify both launches use the same cache root/account namespace without printing their private values. Extend `LocationIndexTests.swift` only for a reproduced missing case. An unchanged usable payload should issue zero scan requests under the existing policy; completed-scan persistence failure must be distinguishable from timeline change.

The Map-only Diff rollout below is still the intended way to avoid whole-library scans after small changes. Existing transport and pure merge code do not yet constitute production integration. Preserve the evidence gates and the documented explicit warm Retry/Rebuild fallback; do not enable Diff merely because an empty response decodes successfully. A HAR around a disposable upload/delete or replacement through the Photos refresh would help establish feed visibility timing, paired with read-only Diff probes if the web app does not call Diff. Large-change, cursor-reset, enumeration, and access-change gates need their own controlled evidence.

Use `SYNO.Foto.Browse.Diff` only to validate and repair the Personal Library location-index payload. Keep other resources cached-first and authoritative once per run. Also implement the requested metadata-only Settings invalidation command across all metadata consumers; that command is deliberately broader than Diff's scope.

The priorities are smooth, useful cached browsing offline or over slow Internet, followed by a cache implementation that is easy to understand and maintain. Fewer requests matter only when they serve those priorities. Stale content remains usable during refresh and after failure; verification controls freshness claims and write/network admission, not whether cached photos can be viewed. Measure time to useful cached interaction and UI stability before counting avoided requests.

## Intended ownership and consumer contract

The end state has three cache freshness rules: conventional metadata validation once per run, location-payload Diff validation, and existing image HTTP validation. Reset adds one shared lifecycle rule, not another freshness system. Keep these rules inside `PhotoCache`; consumers never choose a Diff strategy, inspect a cursor/proof/generation, sequence a fence, or decide whether a server error means rebuild. This exception is maintainable only if the Map coordinator stays small and resource-local; do not build a general proof framework to share a few helper calls.

Preserve `timeline`, `page`, `albums`, thumbnail and original APIs. Map consumers use `locationIndex(retry:)` and receive cached/current records, generic refresh progress and a retryable failure. Cursors, capability evidence, merge strategy and persistence outcome stay internal. Expose a successful metadata-invalidation revision to UI, not reset admission/transaction phases. Match actual ownership: `AppShellView` owns `MapBrowserModel` and viewer presentation; the AppKit browser coordinator in `LibraryBrowserView.swift` owns `LibraryPageWindow`; `LibraryModel` manages its own snapshots, tasks and selection state. Each owner applies the successful revision to its own children through one idempotent invalidation method. Long-lived `PhotoCache` coordinators privately observe the internal reset lifecycle or receive explicit invalidation from their actual owner; do not invent a universal `LibraryModel` relay or add observers to every view/cell. Repository reset owns cancellation/storage; consumer invalidation releases derived state and schedules ordinary demand.

Map publication carries an opaque content revision only for stale click/filter detection; UI forwards it without interpretation. Move map-filter snapshot/section construction from `LibraryModel.openMapFilter` into repository `registerMapFilter(itemIDs:locationRevision:)`, returning descriptor and snapshot. Resolve selected IDs, validate revision, build sections and register atomically on the repository actor. Delete the superseded caller-built snapshot/ID-array registration API after updating tests. Keep camera/clustering/display in the app and Personal Library page filtering in the repository.

## Scope and unchanged behavior

| Resource | Behavior under this alternative |
| --- | --- |
| Personal Library location index | Own opaque cursor/proof inside its payload; empty-interval reuse, bounded item repair, or full scan. |
| Personal Library/Favorites timelines and exact section pages | Preserve `validationRun(for:)`, collection mutation epochs, exact request keys, and authoritative network validation. No Diff call, proof, or membership patching from Map deltas. |
| Album list and opened-album synthesized timelines/pages | Preserve `albumListValidationRun()`, conventional list/scan/page fetching and collection isolation. No album proofs. |
| Session map-filter collections | Continue deriving pages from complete Personal Library sections through the normal page pipeline; keep required-ID completeness checks and bounded session cache. No persistent proof or arbitrary-ID lookup substitution. |
| Thumbnail, viewer preview and original bytes | Preserve opaque revision keys, conditional HTTP requests, current-run validation, content checks, priority promotion, rendition fallbacks and decoded digest identities. |
| Favorites writes/viewers | Preserve optimistic page patch/rollback, write serialization, pending IDs, mutation epochs, authoritative Favorites refresh, and the frozen viewer playlist/ledger. |

An empty Map Diff cannot validate a timeline, page, album, Favorites membership, photo details, or image. Map lookup responses contain only the fields needed for locations and must not be written into exact page cache keys. Do not add a global cursor, generic metadata proof envelope, whole-cache change journal, periodic polling, Shared Space support, or NAS write endpoint. Initial timeline bootstrap remains provisional. External changes after a resource's successful run validation remain outside the session freshness contract.

## Evidence and remaining uncertainty

Preserve these observations in sanitized fixtures and API documentation:

- Diff advertises versions 1–7. `get_version` v1 returns `diff_version` and `version_time`; `get` requires the exact opaque pair. Missing fields returned 120; mismatched and `(0, 0)` pairs returned 700. Error 700 has not been established as expiry of a previously valid pair.
- A two-day-old pair returned 67 unique `item.modify` base objects deterministically on replay and an empty interval from its returned cursor. Those objects did not contain GPS or thumbnail descriptors.
- Controlled upload appeared under `item.modify`; controlled delete appeared as a bare integer under `item.delete`. Unrelated modifications occurred in both intervals. Returned cursors fenced empty.
- A same-ID external overwrite added GPS and changed capture time and thumbnail cache key while retaining thumbnail unit ID. It appeared once under `item.modify`, with no deletion, and authoritative lookup returned the new coordinates. This proves the combined overwrite/reindex path, not isolated GPS-only coverage.
- `Browse.Item.get` v7 accepts `id=[...]` with `additional=["gps","thumbnail"]`. Lookup of the 67 IDs preserved order and returned all rows; documented probes also accepted 100, 500 and 1,000 IDs. Missing IDs are silently omitted, and duplicate requested IDs repeat. Omission is not proof of deletion or lost visibility. Item IDs and thumbnail unit IDs are distinct.
- Empty post-lookup intervals demonstrate quiet-window fences in observed runs; they do not prove universal indexing visibility or completeness.

Accept the existing explicit product assumption that an isolated GPS change/removal or reindex appears under `item.modify`. Synology Photos 1.9.1-10928 has no GPS editor; `Browse.Item.set` with GPS was rejected. Do not invent a GPS write endpoint. A false-empty GPS interval can leave stale pins; metadata-only invalidation below is the recovery path. This residual assumption does not cover unknown access, truncation, or reset behavior.

The vendored `docs/SynologyPhotosAPI/API/SYNO.Foto.lib` advertises Diff but gives no change semantics; `docs/SynologyPhotosAPI/API/SYNO.Foto/SYNO.Foto.Browse.Item.list.md` describes list/GPS fields, not arbitrary-ID lookup. Prefer the observed `id` contract; do not invent `item_ids`, continuation parameters, object-shaped tombstones, or “delete wins” ordering.

## Location validation algorithm

`locationIndex(retry: Bool = false)` first reads and emits compatible cached records without waiting for authentication, timeline, or gate admission. Capture the metadata token before that suspended disk read; recheck before any cached publication. Join one run-local attempt; successful later opens reuse its result even if disk retention failed. Implicit repeated demand replays a memoized failure; `MapBrowserModel.retry()` explicitly starts one new attempt. Authentication retry remains separately controlled by `retryAuthentication()`.

1. Remove `verifiedPersonalTimelineFingerprint()` from Map validation. The Personal Library timeline validates independently; Map may use its latest count as optional estimated progress but must not block cached interaction or its own Diff on a slow timeline request. Do not let Map set the timeline's run marker. Filters use cached personal descriptors/pages provisionally through their ordinary refresh path; unavailable pages report unavailable content without hiding cached pins.
2. With eligible proof, request `changes(since: payload.proof.cursor)`. A complete eligible interval with all four arrays empty reuses the records and commits the returned cursor atomically. No lookup or second fence is needed because no metadata reads intervene.
3. For a bounded item-only interval, reject duplicate IDs, repeated tombstones and modify/delete overlap conservatively into one full baseline attempt. Do not infer event precedence. Lookup every unique modified ID, including IDs absent from the existing map. Require exactly one authoritative result per requested ID, no unexpected IDs and no omissions. A pure delete needs no lookup. Missing modified rows cannot be treated as deleted.
4. `LocationIndexDelta.apply` merges into a candidate by item ID: confirmed deletes remove records; found items with valid coordinates replace/add the entire record (time, coordinates, thumbnail); found items without GPS remove their pin. Follow current `PhotoItem.coordinate` validity rules. Sort full scans and repaired candidates identically by capture time descending then ID ascending. Never mutate/publish the last good map incrementally.
5. After all lookup batches call `changes(since: interval.cursor)`. Only a complete all-four-arrays-empty fence permits commit with its returned cursor. A nonempty fence discards the candidate and allows one full baseline. Never advance the payload cursor from a Favorites write or subtract “known local” changes; they can overlap external edits.
6. Recheck cancellation, reset epoch, metadata generation and job identity before persistence and again before publication. Replace pins once; preserve camera. Persist proof and records as one value; failure to persist may still yield a current run-local result but cannot establish cross-run proof.

Give each published record set a revision and store it in `MapFilterState`. If replacement changes records underlying an existing filter, invalidate that filter/pages, return its browser to Map and close its viewer through reset-safe image release. Cursor-only advancement with identical records does not invalidate filters. Repository registration rejects obsolete revisions atomically; `LibraryModel.openMapFilter` also checks its presentation request identity after awaiting registration so abandoned clicks cannot navigate. This is dependency invalidation, not Diff validation of Personal Library pages.

With evidence-backed usable Diff, no eligible proof, nonempty album arrays, ambiguous/over-limit delta, lookup omission, or rejected cursor permits at most one full baseline per attempt. For unsupported/unproven capability use the warm/cold policy below instead. Obtain A immediately before scanning, walk 1,000-item positional pages with at most two requests in flight and the existing 2,048-page cap, and request `changes(since: A)` afterward. Require the demonstrated complete/stable scan contract, terminal short/empty page, no duplicate scanned IDs, and empty complete fence. Retain a bounded scanned-ID set, located records and at most two pages, not all `PhotoItem`s. A full page at the cap fails rather than saving partial data. Duplicate or nonempty baseline fence retains old pins and reports “Library changed during validation; retry.” Do not loop or save a cursorless candidate after an available fence failed.

After fenced validation ships, unsupported/unproven capability with compatible cached pins leaves them visibly stale/unverified and reports “Showing cached locations; validation unavailable” with Retry. Neither `LocationIndexEvent` nor `MapBrowserModel.Status` may report these pins as ready/current merely because cached records exist; add an explicit cached-unverified presentation state and preserve it on reopen. It does not scan the warm library every run. Cold demand or explicit Retry may perform one conventional scan and save a cursorless payload under the static-during-session assumption; subsequent warm runs display it without claiming current freshness until another scan. Timeout/authentication/transport errors also retain pins without automatic lengthy scans. Unknown malformed responses invalidate reuse; allow a cursorless scan only with unusable capability and cold demand or explicit Retry, never to bless a candidate whose available fence failed. A 700 response may obtain a fresh fenced baseline if possible, never empty success or an inferred expiry label. Remove fingerprint equality at the final switch; counts never establish freshness.

## Bounds, persistence and scoped generations

Use the existing two-slot metadata `NetworkGate` at prefetch priority for each Diff, lookup and scan request. Release between requests; never await child work while holding its required slot. Preserve visible-page promotion and queue bounds. Start with client policies of 2,000 changed IDs, 32 lookup batches, 100 IDs per lookup, and two concurrent lookup requests; these are not server limits. Cancel siblings on every exit. Impose 4 MiB maximum Diff response bytes while receiving in `SynologyClient` (its current buffered `post` is insufficient for a receipt bound); cancel receipt immediately on overflow, before decoding/copying. Use a scoped bounded-response helper, not a rewrite of all HTTP operations. No global interval LRU or per-resource proof request scheduler is needed.

In `DiskCache.swift`, add a separate metadata generation alongside whole-cache `generation`, plus `currentMetadataGeneration()`. Define `MetadataWorkToken` in planned `RepositoryMetadataToken.swift`: repository reset epoch, disk whole/metadata generations, job UUID, collection and mutation epoch where applicable. Capture before the first suspension, then validate after awaits, before publication and at the storage boundary. All metadata mutations, including remove, validation marks, Favorites patch and rollback, must require metadata generation. Image methods continue requiring only whole-cache generation.

Concretely, capture repository-owned epoch/job/collection fields synchronously, then read both disk generations in one actor call and verify the repository fields again before admission. Never assemble a token across a reset and treat it as newly admitted old work. Full clear advances both disk generations; metadata clear advances only the metadata generation. Advance storage metadata generation at reset admission before attempting SQL deletion; never roll it back on failure. Generation advance and delete transaction execute without suspension on the storage actor. A write ordered before storage reset admission may finish and its row may survive failed deletion, but is provisional under the new generation. A pre-reset token reaching storage after admission must be rejected even after rollback.

Add `putMetadata(...expectedGeneration:expectedMetadataGeneration:) -> MetadataStoreResult` with `.stored`, `.generationChanged`, `.notRetained`. Enforce one location writer per metadata generation; an attempt retains ownership through persistence/publication before a successor starts. Retry joins active work, while reset advances storage generation. These invariants avoid a generic row-revision/CAS framework and exposing digest revisions through every `CacheEntry` for this single-writer payload. Encode records/proof in one SQLite row and transaction. Check retention after trimming; silent declined `put` is not persistence success. Crash/fault outcomes are old coherent payload, new coherent payload, or miss; never new cursor with old records. Never separately mark an older row validated after failed storage.

This single-writer argument replaces row CAS only for the location payload. It does not protect exact page writes from same-generation Favorites patch/rollback read-modify-write races, nor does metadata generation replace collection mutation epochs or other shared metadata commit protection. Preserve those resource-specific protections and audit `registerPage`, `patchAffectedPagesBatch` and `rollbackBatchFavoriteCaches` across their storage awaits. If the existing guards permit a stale same-generation overwrite, serialize that page mutation or add a targeted atomic revision-checked commit; do not remove needed protection because the location writer is serialized. Test page fetch versus optimistic patch, rollback versus later patch, and authoritative Favorites refresh independently of Map persistence.

Apply token admission/publication checks to `timeline`, `page`, `initialTimeline`, `registerTimeline`, `registerPage`, `transientPage` in `CachedPhotosRepository+Metadata.swift`; `albums`/`registerAlbumList` in `CachedPhotosRepository+Albums.swift`; map-filter registration/page assembly; and Favorites patch/rollback/refresh in `CachedPhotosRepository+Favorites.swift`. Retain runID, collection and mutation epoch in `validationRun(for:)`; include metadata generation/reset epoch so reset cannot reuse old run markers. Extend `albumListValidationRun()` equivalently. Capture the Favorites refresh token before the network request, correcting its current post-request generation capture. Do not replace any of these authoritative fetches with Diff, change their raw payload formats, or add baseline fences to them.
