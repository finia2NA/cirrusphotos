# Map-only Diff cache validation

Status: alternative implementation plan, not implemented. Reviewed against the source on 2026-10-08. This is an alternative to [whole-app Diff validation](WIP_DIFF_CACHE_PLAN.md), not a prerequisite or an incremental step toward that proposal. Neither alternative is selected by this document.

Use `SYNO.Foto.Browse.Diff` only to validate and repair the Personal Library location-index payload. Keep other resources cached-first and authoritative once per run. Also implement the requested metadata-only Settings invalidation command across all metadata consumers; that command is deliberately broader than Diff's scope.

## Scope and unchanged behavior

| Resource | Behavior under this alternative |
| --- | --- |
| Personal Library location index | Own opaque cursor/proof inside its payload; empty-interval reuse, bounded item repair, or full scan. |
| Personal Library/Favorites timelines and exact section pages | Preserve `validationRun(for:)`, collection mutation epochs, exact request keys, and authoritative network validation. No Diff call, proof, or membership patching from Map deltas. |
| Album list and opened-album synthesized timelines/pages | Preserve `albumListValidationRun()`, conventional list/scan/page fetching and collection isolation. No album proofs. |
| Session map-filter collections | Continue deriving pages from complete Personal Library sections through the normal page pipeline; keep required-ID completeness checks and bounded session cache. No persistent proof or arbitrary-ID lookup substitution. |
| Thumbnail, viewer preview and original bytes | Preserve opaque revision keys, conditional HTTP requests, current-run validation, content checks, priority promotion, rendition fallbacks and decoded digest identities. |
| Favorites writes/viewers | Preserve optimistic page patch/rollback, write serialization, pending IDs, mutation epochs, authoritative Favorites refresh, and the frozen viewer playlist/ledger. |

An empty Map Diff cannot validate a timeline, page, album, Favorites membership, photo details, or image. Map lookup responses contain only the fields needed for locations and must not be written into exact page cache keys. Do not add a global cursor, generic metadata proof envelope, whole-cache change journal, periodic polling, Shared Space support, or NAS write endpoint. Initial timeline bootstrap remains provisional. External changes after a resource's successful run validation remain outside the session freshness contract.

The [architecture](../ARCHITECTURE.md) describes current behavior. [Cache design](WIP_CACHING_PLAN.md) contains older proposed details, including pending album/map work and storage proposals; source is authoritative for implemented behavior. [API evidence](../SYNOLOGY_PHOTOS_API.md#library-change-feed) records the protocol observations.

## Evidence and remaining uncertainty

Preserve these observations in sanitized fixtures and API documentation:

- Diff advertises versions 1–7. `get_version` v1 returns `diff_version` and `version_time`; `get` requires the exact opaque pair. Missing fields returned 120; mismatched and `(0, 0)` pairs returned 700. Error 700 has not been established as expiry of a previously valid pair.
- A two-day-old pair returned 67 unique `item.modify` base objects deterministically on replay and an empty interval from its returned cursor. Those objects did not contain GPS or thumbnail descriptors.
- Controlled upload appeared under `item.modify`; controlled delete appeared as a bare integer under `item.delete`. Unrelated modifications occurred in both intervals. Returned cursors fenced empty.
- A same-ID external overwrite added GPS and changed capture time and thumbnail cache key while retaining thumbnail unit ID. It appeared once under `item.modify`, with no deletion, and authoritative lookup returned the new coordinates. This proves the combined overwrite/reindex path, not isolated GPS-only coverage.
- `Browse.Item.get` v7 accepts `id=[...]` with `additional=["gps","thumbnail"]`. Lookup of the 67 IDs preserved order and returned all rows; documented probes also accepted 100, 500 and 1,000 IDs. Missing IDs are silently omitted, and duplicate requested IDs repeat. Omission is not proof of deletion or lost visibility. Item IDs and thumbnail unit IDs are distinct.
- Empty post-lookup intervals demonstrate quiet-window fences in observed runs; they do not prove universal indexing visibility or completeness.

Accept the existing explicit product assumption that an isolated GPS change/removal or reindex appears under `item.modify`. Synology Photos 1.9.1-10928 has no GPS editor; `Browse.Item.set` with GPS was rejected. Do not invent a GPS write endpoint. A false-empty GPS interval can leave stale pins; metadata-only invalidation below is the recovery path. This residual assumption does not cover unknown access, truncation, or reset behavior.

The vendored `docs/SynologyPhotosAPI/API/SYNO.Foto.lib` advertises Diff but gives no change semantics; `docs/SynologyPhotosAPI/API/SYNO.Foto/SYNO.Foto.Browse.Item.list.md` describes list/GPS fields, not arbitrary-ID lookup. Prefer the observed `id` contract; do not invent `item_ids`, continuation parameters, object-shaped tombstones, or “delete wins” ordering.

### Map-specific enablement gates and useful captures

Implement transport/reset/merge infrastructure before all evidence exists, but do not enable cross-run location proof reuse until the mandatory gates pass. Until then perform a conventional full location scan once per run, without fingerprint-based freshness claims. Record capability evidence against the observed server/Photos version; unknown or changed capability defaults to conventional scanning until reassessed.

| Gate | Exact remaining observation |
| --- | --- |
| Mandatory: interval completeness and large changes | Save cursor A and complete authoritative ID inventory; perform user-controlled bulk import/delete exceeding the 2,000-ID/4 MiB client policy, then compare repeat `Diff.get(A)` responses against the complete before/after inventory. Inspect actual truncation/continuation/termination fields. A client cap cannot detect a silently truncated small response; absence of trustworthy completeness blocks reuse. No invented pagination. |
| Mandatory: cursor reset/rejection | Retain a once-valid pair and test aged rejection or a user-controlled service restart/reindex/reset in a disposable environment. Compare old-pair behavior with `get_version` and authoritative inventory. Rule out silent empty success after cursor namespace reset. `(0,0)` error 700 is insufficient. Unknown 700 invalidates that attempt's proof but must not be labeled confirmed expiry. |
| Mandatory: scan/lookup/feed visibility | Around upload, delete, and same-ID overwrite, record when authoritative lookup/list first changes versus when Diff becomes nonempty; also change during a positional scan and between lookup and fence. A reproducible authoritative change followed by a false-empty fence fails this gate. Existing quiet fences alone do not settle delayed indexing. |
| Mandatory: Personal Space access changes | Under a controlled account, revoke/restore visibility of disposable items/folders; compare full location scan and lookup with Diff. Silent visibility loss with empty Diff blocks reuse unless an independently proven access check is designed. Cached offline pins are not an access verification claim. |
| Useful: isolated GPS removal/change | Externally edit/reindex a disposable file while preserving capture time and other metadata where possible. Capture File Station replacement and Photos details reload; compare ID, coordinates, time, thumbnail descriptor and Diff. Accepted residual assumption means inability to isolate this is not a gate. |
| Useful: repeated/conflicting item changes and album separation | Repeatedly edit then delete a disposable item; inspect duplicate/overlap behavior. Capture normal-album-only edits to assess whether album arrays can safely be ignored for Map. Until proven, conflicts/nonempty album arrays trigger conservative rebuild, so these probes are not required to ship that fallback. |

For every controlled action save A, authoritative before/after state, two reads from A and a fence from the returned cursor. A HAR should cover the named web interaction through the Photos refresh, including Diff and item follow-ups if present; pair read-only probes with the HAR if the UI does not issue Diff. Sanitize credentials, URLs, filenames and coordinates. Retention beyond two days is useful operational data, not a guessed TTL. Favorite/album membership and EXIF-page coverage gates from the whole-app proposal are intentionally not required here. All write probes are user-performed or require explicit approval; this plan authorizes none.

## Location validation algorithm

`locationIndex(retry: Bool = false)` first reads and emits compatible cached records without waiting for authentication, timeline, or gate admission. Capture the metadata token before that suspended disk read; recheck before any cached publication. Join one run-local attempt; successful later opens reuse its result even if disk retention failed. Implicit repeated demand replays a memoized failure; `MapBrowserModel.retry()` explicitly starts one new attempt. Authentication retry remains separately controlled by `retryAuthentication()`.

1. Join ordinary Personal Library timeline validation for startup coordination and estimated scan progress. Rename `verifiedPersonalTimelineFingerprint()` to `verifiedPersonalTimelineForLocations()`; its value is not Map freshness proof. Do not let Map set that timeline's run marker.
2. With eligible proof, request `changes(since: payload.proof.cursor)`. A complete eligible interval with all four arrays empty reuses the records and commits the returned cursor atomically. No lookup or second fence is needed because no metadata reads intervene.
3. For a bounded item-only interval, reject duplicate IDs, repeated tombstones and modify/delete overlap conservatively into one full baseline attempt. Do not infer event precedence. Lookup every unique modified ID, including IDs absent from the existing map. Require exactly one authoritative result per requested ID, no unexpected IDs and no omissions. A pure delete needs no lookup. Missing modified rows cannot be treated as deleted.
4. `LocationIndexDelta.apply` merges into a candidate by item ID: confirmed deletes remove records; found items with valid coordinates replace/add the entire record (time, coordinates, thumbnail); found items without GPS remove their pin. Follow current `PhotoItem.coordinate` validity rules. Sort full scans and repaired candidates identically by capture time descending then ID ascending. Never mutate/publish the last good map incrementally.
5. After all lookup batches call `changes(since: interval.cursor)`. Only a complete all-four-arrays-empty fence permits commit with its returned cursor. A nonempty fence discards the candidate and allows one full baseline. Never advance the payload cursor from a Favorites write or subtract “known local” changes; they can overlap external edits.
6. Recheck cancellation, reset epoch, metadata generation and job identity before persistence and again before publication. Replace pins once; preserve camera. Persist proof and records as one value; failure to persist may still yield a current run-local result but cannot establish cross-run proof.

Give each published location-record set a revision and store its revision in `MapFilterState` when `registerMapFilter` creates a collection. If a successful replacement changes records underlying an existing filter, invalidate that filter and its cached pages, return its browser to Map and close its viewer through the reset-safe image-release path. Cursor-only advancement with identical records does not invalidate filters. `LibraryModel.openMapFilter` must check the revision again after awaiting registration so a click on obsolete pins cannot register a stale collection. This is session dependency invalidation, not Diff validation of underlying Personal Library pages.

For no eligible proof, nonempty album arrays, ambiguous/over-limit delta, lookup omission, or rejected cursor, run at most one full baseline per explicit attempt. If Diff is usable, obtain A immediately before scanning, walk 1,000-item positional pages with at most two requests in flight and the existing 2,048-page cap, and request `changes(since: A)` afterward. Require a terminal short/empty page, no duplicate scanned IDs, and an empty complete fence. Retain a bounded scanned-ID set for duplicate detection, located records and at most two pages, not all `PhotoItem`s. A full page at the cap fails rather than saving partial data. A duplicate or nonempty baseline fence retains the old payload and reports “Library changed during validation; retry.” Do not loop or save a cursorless candidate after an available fence failed.

When capability is definitively unsupported or required evidence is unavailable, a successful conventional scan produces a cursorless payload under the existing static-during-session assumption; it must scan again on next run. Delete the fingerprint-equality shortcut. This costs a scan per run without trustworthy Diff and fixes the same-count GPS/identity freshness gap. A timeout, authentication failure or transport error retains cached pins and exposes Retry, without automatically launching a lengthy scan. Unknown malformed responses invalidate reuse; allow one cursorless full scan only when capability is explicitly classified unusable, not as recovery from a failed consistency fence. A 700 response requires a fresh baseline attempt if possible, never empty success or an inferred expiry label.

## Bounds, persistence and scoped generations

Use the existing two-slot metadata `NetworkGate` at prefetch priority for each Diff, lookup and scan request. Release between requests; never await child work while holding its required slot. Preserve visible-page promotion and queue bounds. Start with client policies of 2,000 changed IDs, 32 lookup batches, 100 IDs per lookup, and two concurrent lookup requests; these are not server limits. Cancel siblings on every exit. Impose 4 MiB maximum Diff response bytes while receiving in `SynologyClient` (its current buffered `post` is insufficient for a receipt bound); cancel receipt immediately on overflow, before decoding/copying. Use a scoped bounded-response helper, not a rewrite of all HTTP operations. No global interval LRU or per-resource proof request scheduler is needed.

In `DiskCache.swift`, add a separate metadata generation alongside whole-cache `generation`, plus `currentMetadataGeneration()`. Define `MetadataWorkToken` in planned `RepositoryMetadataToken.swift`: repository reset epoch, disk whole/metadata generations, job UUID, collection and mutation epoch where applicable. Capture before the first suspension, then validate after awaits, before publication and at the storage boundary. All metadata mutations, including remove, validation marks, Favorites patch and rollback, must require metadata generation. Image methods continue requiring only whole-cache generation.

Concretely, capture repository-owned epoch/job/collection fields synchronously, then read both disk generations in one actor call and verify the repository fields again before admission. Never assemble a token across a reset and treat it as newly admitted old work. Full clear advances both disk generations; metadata clear advances only the metadata generation. SQL generation checks and the metadata delete transaction execute without suspension on the storage actor.

Add `putMetadata(...expectedGeneration:expectedMetadataGeneration:expectedRevision:) -> MetadataStoreResult` with `.stored`, `.generationChanged`, `.superseded`, `.notRetained`. Expose existing SQLite `entries.digest` as row revision in `CacheEntry`, distinguishing expected-absent from no revision comparison. Use generation plus compare-and-swap for the location candidate so an old proof extension cannot overwrite a newer location payload. Encode records/proof into the same SQLite metadata row and write in one transaction. Check retention after trimming; a silent declined `put` is not successful persistence. Crash/fault outcomes must be old coherent payload, new coherent payload, or cache miss; never new cursor with old records. Do not independently call `markValidated` to bless an older location row after failed storage.

Apply token admission/publication checks to `timeline`, `page`, `initialTimeline`, `registerTimeline`, `registerPage`, `transientPage` in `CachedPhotosRepository+Metadata.swift`; `albums`/`registerAlbumList` in `CachedPhotosRepository+Albums.swift`; map-filter registration/page assembly; and Favorites patch/rollback/refresh in `CachedPhotosRepository+Favorites.swift`. Retain runID, collection and mutation epoch in `validationRun(for:)`; include metadata generation/reset epoch so reset cannot reuse old run markers. Extend `albumListValidationRun()` equivalently. Capture the Favorites refresh token before the network request, correcting its current post-request generation capture. Do not replace any of these authoritative fetches with Diff, change their raw payload formats, or add baseline fences to them.

## Metadata-only Settings invalidation

Add `Button("Clear Metadata Cache")` in `Sources/SynoTimelineApp/CacheSettingsView.swift`, wired to `LibraryModel.clearMetadataCache()` and `CachedPhotosRepository.clearMetadataCache()`. Help text: “Remove timelines, loaded sections, album metadata and the map index. Keep thumbnails, previews and originals.” Keep existing “Clear Cache” for all data. Disable both during either reset; expose a short inline error and refresh usage. No new keyboard shortcut is needed.

Implement one replaying repository reset stream in planned `CachedPhotosRepository+Reset.swift`: `cacheResetStates() -> AsyncStream<CacheResetState>` carrying monotonically increasing epoch, scope (`metadata`/`all`) and phase (`idle`/`resetting`/`completed`/`failed`). Register lifetime listeners before consumers load; finite resource streams cannot deliver a later reset. One state machine handles both actions, serializes reset attempts and pauses new metadata admission while resetting. Existing generation checks alone do not invalidate already displayed metadata.

1. Enter resetting and advance repository admission epoch before awaiting disk. Cancel metadata read jobs and reject late callbacks, clear completed-attempt memos, but preserve auth and admitted favorite writes. Temporarily prevent new selection-based writes; already submitted writes must finish and retain honest partial-success/rollback outcomes.
2. `DiskCache.clearMetadata()` transactionally deletes all `.timeline`, `.page`, `.albumList`, `.locationIndex` rows (including album snapshots stored as timelines). On success advance metadata generation only. Do not call `clear()`, delete image files, trim images, change image validation runs, or rebuild the index. On SQL failure roll back deletion; report failed reset, keep prior disk rows and resume admission under the new repository epoch. Old jobs remain obsolete; retry/reload current consumers safely. Do not show successful empty metadata on failure.
3. On success clear `latestTimelines`, album list, page work/epoch/promotion maps, map records/proof, filters/pages/LRU and run validation state. Keep collection mutation epochs monotonic and preserve live Favorites write/override state. A pre-reset favorite cache backup must never restore metadata after reset. Post-reset authoritative Favorites refresh uses a new token and waits for admitted writes; never duplicate a NAS write.
4. Publish completed. Each window clears derived metadata, selection commands and ordinals, verification and pending metadata resolvers. Active destinations refetch conventionally; Map starts a new baseline only when demanded. Saved navigation anchors/preferences may remain and reconcile against refreshed metadata; they are user state, not metadata cache.

## UX, observability and acceptance

Extend `LocationIndexEvent` with phases for checking changes, repairing changed items and rebuilding. Display cached pins during validation and on failure with explicit Retry; cold failure is not an empty-success map. Delta progress counts resolved IDs; scan progress counts scanned items against estimated total. Avoid reclustering identical records merely to change verification state. No periodic retries, new shortcut, location labels or image-download sweep.

Log aggregate strategy, delta size, request/byte counts, fallback reason, scan count, elapsed time, cancellation, persistence outcome and gate contention. Do not log raw cursors, IDs, filenames, coordinates, tokens or authenticated URLs. Distinguish verified-in-memory from stored-for-next-run, and unknown rejection from confirmed expiry. Compare cached first paint and visible scrolling while Map uses the metadata gate.

Manual acceptance: establish a cold fenced baseline; relaunch unchanged and verify one Map Diff avoids the minutes-long scan while non-Map request behavior remains unchanged; exercise user-performed upload/delete/overwrite and confirm pins/time/thumbnail descriptors; verify offline cached Map and explicit retry; use fake fixtures for destructive/reset edge cases unless separately approved. Open a Map filter, Info panel, Favorites viewer and range downloader in two windows, then clear metadata during image transfers. Confirm filters return to Map, stale commands stop, metadata reloads, camera/appropriate anchors survive and downloads/image cache survive. Repeat full clear and verify its all-data scope. Measure the cursorless per-run fallback cost explicitly.

Acceptance requires evidence-gated Map proof, atomic payload/cursor persistence, bounded repair/scan work, deterministic race tests and fully functional metadata-only recovery. Diff must have no authority outside the location payload. No global cursor, fingerprint freshness shortcut, migration, hidden image validation change or weakened Favorites/viewer invariant may remain.
