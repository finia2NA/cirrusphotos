The proxy streamed response bodies through rather than buffering them; it recorded request and response timestamps, ranges, and completed transfer sizes. It did not record player events or the number of bytes received before an interrupted response.

The user's playback observation and the interrupted long-video response are consistent with progressive playback, but the capture does not measure the exact first-frame time or bytes consumed at that moment. Early endings are recorded as proxy errors, without enough detail to distinguish deliberate cancellation from other disconnections.
- The recorded tail reads preceded the main media reads in both cases. This may reflect the files' container layout; the capture does not establish the container structure or Android's internal player decisions.

## Implication for this app

The Android client does not split these observed requests into 64 KiB HTTP ranges. Its open-ended requests allow a streaming consumer to receive data while the server continues sending. The current macOS client can similarly deliver each available cache segment to AVFoundation without waiting to assemble a 4 MiB response. A subsequent transport change could stream larger HTTP responses incrementally while retaining bounded caching, seek cancellation, authenticated transport, and cache validation. These observations alone do not establish an optimal request or cache-segment size.
